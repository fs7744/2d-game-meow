## 骨骼编辑节点：拖关节 + 换视觉方向（用户点名要的交互层）

用户看完「Qwen 双图条件」结论后要求做 2D 骨骼编辑器，并问能否换视觉方向。
做了，且实测三方向都生效。

### 实现
- 新组件 `web/src/components/SkeletonEditor.tsx`：SVG 渲染 OpenPose-18
  （18 色 19 边，严格复刻 `tools/make_pose.render`），拖圆点改关节、
  深度滑块改 z、7 个姿势预设、8 方向按钮 + 任意角度滑块。
- **伪 3D 投影**是换方向的关键：关节存 (x,y,z)，
  `rx = 0.5 + (x-0.5)*cos(a) + z*sin(a)`，ry=y。
  只有 2D 的话肩膀一转就叠成一个点；拖动时屏幕横向位移按 (cos a, sin a)
  分解回 x/z，侧面视角下横向拖自动变成改深度。
- 新节点 kind=`poseedit`，状态存 `GenNode.skeleton`（可持久化），
  导出 PNG → `/upload` → 挂到 `node.image`，于是能像图片节点一样连线。
- `NodePatch` 要加 `'skeleton'`；`sourcePathOf` 要认 `poseedit` 的 image.path。

### 两个必须配套的坑
1. **`refcond.MODES` 加 `skeleton`**：骨架图上没有真人，走 `auto` 会因
   FasterRCNN 检不到人体而静默降级成 outline（剪影），把骨架毁成黑图。
   前端检测到上游是 poseedit 时自动把 pcRefMode 切成 skeleton。
2. **方位角补方向词**：骨架朝向信息 Qwen 有时读不准（侧面骨架仍出正面人），
   提交时自动追加 `viewing direction: side view, facing right` 之类短语，
   不改用户写的 prompt。这是零成本双保险。

### 实测（768²/8 步，同角色图 + 三方向骨架）
正面 / 侧面 / 背面**都正确**：背面见后脑与背部，侧面身体明显收窄。
侧面双臂投影会重叠（符合真实），所以预设给左右手腕加了前后深度差
（z 从 ±0.05 拉到 ±0.14）。
耗时：单张 20~46s，同进程连续生成降到 20s 左右。

### 偶发慢（未复现，别乱改）
20 步连续生成时观察过一次第二张 252s（正常 24s），但 8 步连续三次复测
46/24/20s 正常，文生图 8 步连续两次 18/13s 也正常。判断是本机 32G 内存
换页偶发（text_encoder 16G 在 CPU），不是管线 bug。
`enable_model_cpu_offload` 的 hook 链本身没问题，别贸然改成全驻留 GPU
（text_encoder 16.3G + transformer 6.6G 会超 24G）。

### 验证
前端 smoke 326/326（新增 7 条骨骼编辑器用例），
后端 test_review_fixes + test_review_p1 + test_api + test_refprep 83 passed。

## 骨骼编辑：从用户图片自动摆姿势（用户追问"能自动吗"）

**能，姿势自动、方向手动。** 链路：编辑器「📷 从图片」→ `/upload`
→ 后端 `POST /pose/extract` 跑本机 DWPose（FasterRCNN + RTMPose，
`normalized_points` 返回 0~1 归一化 18 关节）→ 前端 `skeletonFromPoints`
补深度 → 可旋转骨架 → 点方向按钮 → 导出。

### 关键决策
- **不改 `node.image`**：那个字段挂的是导出的骨架图（连线源）。
  把原图写进去会让下游角色迁移拿到原图而不是骨架，方向无从谈起。
- **2D→3D 深度是启发式**：`SIDE_Z` 按左右侧分配（右 -0.04..-0.12、
  左 +0.04..+0.12，手腕/脚踝加大前后差）。目标是可辨识（别叠成一条线），
  不是物理精确。实测真人照 18/18 关节，0/90/180° 三方向都还像人形。
- **正/背面在 2D 骨架上对称，分不出**：后端只在肩宽 < 0.07 时给侧面猜测
  （`azimuth_guess`，仅提示用），前端导入一律 azimuth=0，
  避免对已经是侧面的图做二次旋转。
- 检测器只认真人/写实人像（COCO 训练），像素/插画必失败 →
  422 错误里直接给"用预设手动摆 / 走轮廓模式"的下一步。

### 安全
新写 `_readable_asset_path`（只读版：在 assets 内 + 是图片文件），
**不复用** `_safe_asset_path`（那是删除接口的，带"不能删 uploads/index"
等额外规则会误伤读图）。TestClient 验证路径穿越 `../../Windows/win.ini` → 400。

### 验证
- 后端 `TestClient`：真人照 18/18 关节、guess=0；路径穿越 400
- 前端 smoke 330/330（新增 4 条：文件入口/导入后关节坐标被替换/
  toast 带 18/18 与朝向猜测/无脚本错误；fetch mock 加 `/pose/extract`）
- 后端 test_review_fixes + test_review_p1 + test_api 64 passed

## Qwen-only 收尾：四个「做不到」的工作流全部落地 + 显存/内存优化

用户指令：review PLAN-QWEN-ONLY.md，自己定计划，用 Qwen-Image-2.1 实现**所有**功能，
优化生成质量与显存/内存，做不到的写进文档。

### 落地（十个工作流现在全通）
- w3 局部重绘：整图指令改图 → 蒙版贴回。**选区外最大差恒为 0**（写进 meta 自检）。
- w5 局部 AI 重绘：同一个机制，保留 `strategy="crop"` 做对照（默认 whole）。
- w4 姿态序列：逐帧「骨架当参考 + 指令」→ 尺度归一 → 脚底对齐 → 打包。
- wss 序列帧替换：逐帧双图条件（角色 + 轮廓）→ 共享色板 → 打包。
- `engine._ARCH_WORKFLOWS["qwen21"]` 全开 + 新增 `_APPROX`，前端节点卡头显示「近似」角标。

### 质量上真正起作用的四件事（都有实测）
1. **条件图分辨率对齐**：管线 `output_resolution` 默认 1024，768 出图却按 1024 编码参考图
   → 尺度错档 + 多 78% 图 token。传成目标边长后 -11% 耗时 / -16% 峰值。
2. **逐帧尺度归一**（`postprocess.normalize_sequence`）：Qwen 没有 ControlNet，
   同段 3 帧主体高度差 3 倍（最小只占 2.1%）。归一后 3/3 可交付（原来 1/3）。
   alpha 必须 NEAREST 缩放，LANCZOS 会长毛边让帧高逐帧飘 5~7px。
3. **条件图灰度化**（`_qwen_cond_image`）：彩色骨架的关节点颜色会被抄进成品
   （实测画出「红色浮空帽子」= 骨架的鼻子点）。黑底反相成白底深线后消失。
4. **步数下限 24**：同 seed 42、768²，12 步没有头、16 步四肢断、20 步可用但腿细、
   24 步完整。默认从 20 提到 24。

### 显存/内存
- 文本编码器（Qwen3-VL 8.77B，bf16 16.3G）是双料峰值。`tools/make_qwen_fp8.py`
  离线逐输出通道量化成 fp8 8.8G：**峰值 16.59→11.41GB（-31%）、快 25%、内存 -7.5G、
  加载 -44%**。同 seed 平均差 1.10/255（>128 的像素 0.24%）。
  开关 `MEOW_QWEN_TEXT_FP8=0`。
- 坑：`_FP8Linear` 的 `sc[:, None]` 遇到 `[out,1]` 形状会广播成 3 维权重，
  F.linear 报 "t() expects a tensor with <= 2 dimensions"（报错点在 vision tower 里，
  完全看不出是 scale 形状）。已改成先 reshape(-1)。

### 测试
- 新增 `tests/test_qwen_workflows.py`（19 条，monkeypatch 掉模型调用，7s 跑完）：
  能力表/近似标记/选举区外不变/output_resolution 真传下去/尺度归一/透明 alpha。
- **全量第一次跑出 45 失败**：全是 SD 权重归档后的 `FileNotFoundError`。

## 「抠图把脸抠掉」：透明底没生效 + 已有 alpha 被无视 + 送进去的图是坏的

用户问「有些抠图怎么把脸抠掉了，不是 Qwen 支持透明背景吗」。查下来三件事叠加，
没有一件是模型不行（提交 7319148）。

### 1. 提示词和透明声明打架（根因）
`transparent=True` 只加了两句 alpha 声明，但正文若还写着 `plain white background`，
那是个**正面要求**。同 seed 42 / 768²：
- 带这句：前景 81.5%、全透明 3.4%、**中间值 77.5%**（alpha 是一层雾）
- 不带：前景 31.0%、全透明 67.8%、中间值 2.9%（干净）
→ `generate._strip_bg_words`，清掉 white/solid/simple/flat background 一类措辞
+ 收掉悬空介词；改动记 `meta.prompt_bg_stripped`。

### 2. `matte_auto` 从不看输入 alpha，一律重抠
Qwen 出图本就带 VAE 第 4 通道。新增 `matte.alpha_trust`（a0≥10%、mid≤12%、fg 1~95%），
三条满足就原样复用（`backend="alpha"`，IoU 1.000）；雾状才真重抠；
显式 `u2net`/`color` 后端不走这套判断。

### 3. `matte_ai` 把透明区当内容喂给分割模型
原来 `img.convert("RGB")` 只是丢掉 alpha，透明区仍是 VAE 噪声色。改 `flatten_white`
合成白底；再补 `fill_holes` 补内部洞（只填不与边界连通的，两腿之间不填）。

### 已知限制（PLAN §4.9）
白毛/白甲 + 白底：直接送 RGB → 丢头顶+胸口（前景 20.9%）；合成白底 → 丢两条腿
（15.6%）。各丢不同部位，**边界被切掉的部分补不回来**。正解是勾透明底别抠图。
逐帧（w4/wss）**不能**开透明底：实测骨架线会被画进成品（角色身上多出棍子）。

### 验证
- 端到端：透明+抠图同开 → stripped=True、matte 被跳过、fg 31.0% / a0 67.8%，
  成品完整无白边。
- 测试 +7（test_matte 6 条、test_qwen_workflows 1 条）；全量 344 passed / 86 skipped。

## 调研 RunComfy 的 10 个 Qwen-Image-2.1 工作流 → 推翻两条硬限制 + 三项新能力

用户给了 https://www.runcomfy.com/comfyui-workflows/models/qwen-image-2.1，
逐页抓了 10 个工作流 + 查 ComfyUI 源码核实机制。**结论比预期大**。

### 推翻 1：Qwen-Image-2.1 能做**真·蒙版 inpaint**（§4.1 已作废）

ComfyUI 的 `Qwen Image 2.1 Inpainting | No-Offset Edits` 用的**就是标准 2.1 权重**
（没有专用 inpaint 权重）。机制两件事：
1. `SetLatentNoiseMask`：初始 latent 蒙版内换噪声
2. **采样器级**的 `denoise_mask`：每步把蒙版外拉回原 latent
   （`comfy/samplers.py:641-642`：`out = out*denoise_mask + latent_image*latent_mask`）

第 2 步与权重无关 → diffusers 用 `latents=` + `callback_on_step_end` 复刻。
核心公式（flow matching）：`x_t = (1-σ)·x0 + σ·ε`。

**实现** `workflows/qwen_mask.py`（60 行）。**三个坑（都踩过）**：
1. pack/unpack **必须用管线自己的** `_pack_latents`/`_unpack_latents`——
   Qwen-2.1 的 latents 是 **2×2 patchify** 过的（管线里 `latents.shape[1]//4`
   是证据），手写 transpose+reshape → 满屏彩色条纹
2. 条件图 latent **必须与管线内部算的那份逐字节一致**——管线会用
   `output_resolution` 经 `calculate_dimensions` 重算条件图尺寸 → 同样条纹
3. **VAE 只吃 RGBA**（4 通道），给 RGB 报 "expected 4 channels, got 3"

**实测**：768²/20 步 ~15s，蒙版外最大像素差 19~46（视觉无差，差异来自 VAE
重建），选区内指令**准确执行**（"盔甲改翠绿"→ 选区变绿、脸与背景不动）。
**工作尺寸下限 768**：512²（latent 32×32）选区**没被改**（蒙版糊成一个点）。

w3/w5 默认走 `strategy="mask"`；旧的 "whole"（逐点 0 但模型看不见蒙版）留作对照。
`engine._APPROX["qwen21"]` 从 4 项减到 2 项。

### 推翻 2：Qwen **能挂 LoRA**（fp8 量化后也行）

diffusers 的 LoRA 层包在 `nn.Linear` **外面**，fp8 的 `w_fp8` 在 forward 里
反量化、LoRA 分支并联 → **不冲突**。
实测 AnyAngle（rank24/384 张量）：1440 个 LoRA 模块生效，出图只慢 1.1s
（12.6→13.7s），**效果可见**（带 LoRA 明显是右侧 3/4 视角）。

**格式坑**：ComfyUI 格式（`diffusion_model.` + `lora_A/B`）与 diffusers 原生
（`transformer.` + `lora.down/up`）键名不同，**ComfyUI 格式挂上去会静默不生效**
（比报错更坏）。转换器 `tools/convert_lora.py`（A→down、B→up，**同名映射**）。

### 推翻 3：「HF 下载被代理挡住」是误判

**用户提供了可用代理 `http://127.0.0.1:7897`**。加上后 `huggingface.co` 直连
也能通，hf-mirror 约 1.8MB/s（比裸连 430KB/s 快 4 倍）。
下载的文件会比标称大几十 KB（服务端末尾多返回内容），
用 `safetensors` 重新 `save_file` 一次即可对齐。

### 新能力：Lightning 少步蒸馏（逐帧 37s → 9.3s）

`lightx2v/Qwen-Image-2.1-Lightning`（64MB，**diffusers 原生格式**）：

## ControlNet Union 端到端跑通（2026-10-30 晚）

权重 7.55GB 下完 → strict 加载 180 key 全对 → 控制确实生效。

### 四个必须踩准的坑（漏一个就出废图）

1. **条件 latent 要做 mean/std 归一化**：管线 `_encode_vae_image` 是
   `(x - latents_mean) / latents_std`（pipeline_qwenimage21.py:448）。
   漏掉 → 尺度差几倍 → skip 把 hidden 打成 NaN → **出图全黑**。
2. **control block 必须有（无参）LayerNorm**：base block 是
   `hidden + tanh(gate)*attn(norm(hidden))`，有门控又有归一化。裸写
   `x = x + attn(x)` 会让残差在 16 层指数放大：skip |mean| 从 0.10 涨到 27.25
   （hidden 才 1.7，15.8×）→ 采样崩。官方 180 key 里没有 norm 权重，
   所以用 `elementwise_affine=False`（不产生 key，加完仍是 180）。
   加上后各层比值稳定 0.17~0.24。
3. **joint 序列要补文本 token 的 0**：block 收到 `[文本, 图像]`，控制分支只产
   图像那部分。768² 下 2334 vs 2304，差 30 = 提示词长度。图像在**末尾**
   （`cat([text, zeros(target//4)])` 再按 image_pad_mask 展开，文本 repeats 恒为 1）。
4. **mask 通道填 1 不是 0**：官方文档说 zero-pad，但实测填 0 控制力只有一半
   （同 scale 像素差 40 vs 80）。

### 强度标定（768² pose）

| 步数 | 可用 scale | 像素差 |
|---|---|---|
| 8 (Lightning) | 0.35~0.5 | 62~126 |
| 24 | 0.1~0.25 | 14~83 |
| 40（官方） | 1.0 | — |

**步数越多可承受强度越低**：skip 是常量、每步都注入，低噪声后期占比越来越大，
最后变成"照抄条件图"（实测 24 步/0.6/全程 → 出图就是骨架本身的彩色线段）。
`--end` 限步和 sigma 衰减都只能缓解，**没根治**。官方 1.0 能跑 40 步说明注入时序
与我们不同（大概 VACE 风格按 sigma 缩放），要追上强度得改时序。

### 实测数字（RTX 4090 24GB / 768²）

## ControlNet Union 改成双流（VACE 风格）—— 一次性跳连是错的

起因：用户选「按 sigma 缩放冲官方强度」。查官方代码时发现根本不是缩放的
问题，而是**结构理解错了**。ComfyUI PR #16519 `comfy/ldm/qwen_image21/model.py`：

```python
def init_stream(self, x, control, prefix_len):
    joint = torch.zeros_like(x)
    joint[:, prefix_len:] = self.control_img_in(control)
    return self.control_blocks[0].before_proj(joint) + x    # ★ 要加回 base hidden
def step(self, index, c, mod, pe, attn_fn, ...):
    c = block(c, mod, pe, attn_fn, ...)                     # ★ 完整 block，吃 modulation
    return c, block.after_proj(c)
```

**两个要害**：
1. control block 是 **base block 的完整副本**（官方 `QwenImage21FunControlBlock`
   继承 `QwenImage21TransformerBlock`），吃 modulation + rotary_emb
2. **每步都重跑整条控制流** → skip 随 timestep 变化

### 结构对账（关键验证）
`QwenImage21TransformerBlock` 的 state_dict 只有 **9 key**（attn 6 + img_mlp 3，
norm 是 elementwise_affine=False 无参）。于是：
`16×9 + 16×2(after_proj) + 2(before_proj 仅 block0) + 2(control_img_in) = 180` ✓

必须 **继承**而不是组合：包一层会让 key 变成 `block.attn.to_q.weight`，多 `block.` 前缀。

真实参数形状（实测）：`hidden_states [1,1035,4096]`、`modulation [2,16384]`、
`rotary_emb [1035,64] complex64`、`target_token_mask [1035,] bool`、
`attention_mask/key_valid` 都是 None。

### 改造后效果（对比旧的一次性实现）
| | 旧（一次性跳连） | 新（双流） |
|---|---|---|
| 24 步 scale 1.0 | 彩线碎片（崩） | 不崩（像素差 76） |
| 24 步甜点 | 0.1~0.25，出"迈步" | **0.4**，出双腿大开下蹲弓步 |
| 8 步甜点 | 0.35~0.5，出"迈步" | **0.6**，出双腿大开+双臂外张，逐点贴合 |
| 每步 skip | 恒定（常量偏置） | U 型 0.352→0.273→0.393 ✓ |

**拐点很陡**：24 步 0.4 好 / 0.45 糊 / 0.5 空白；8 步 0.6 好 / 0.8 空白。
强度必须按步数分开给。

### 代价
8 步 7.5s → **9.4s**（+25%），因为控制流每步多跑 16 个完整 block。
24 步 14.0s → 17.3s。显存不变（peak 18.7GB）。

### 去掉的东西
- 不再需要「文本 token 补 0」的 hack（joint 序列整条给 control 流，文本行留 0）
- 不再需要手补无参 LayerNorm（完整 block 自带 + 吃 modulation，那是治标）
- `--end` / `--decay` 两个旋钮留着但默认不启用（已无必要）

`test_qwen_workflows` 28 passed。文档 §2.15 / §4.3、README 已同步。

## 二轮修复：终于能出完整角色了（2026-10-31 凌晨）

用户反馈"效果还是不行"。查 VideoX-Fun 官方实现（`qwenimage21_transformer2d_control.py`
+ `pipeline_qwenimage21_control.py`）后找到 **三个真根因**，都不是强度问题。

### ① 有 control 时必须关 KV cache（最隐蔽）

pipeline 的 `use_kv_cache` **默认 True**：文本 token 当 prefix 缓存，之后每个
block 只处理**图像** token（768² 下 2304），而 control 链算**完整 joint**
（2331 = 2304 + 27 文本）。两者对不上，hint 硬塞进图像段 → 信号全错。

报错现场：`image_pad_mask 长度 2331 与 joint 长度 2304 不一致`。
官方实现里就有 `cache_enabled = ... and control_context is None`。

修：`pipe(..., use_kv_cache=False)`。

### ② mask 通道填 0，不是 1（之前判断反了）

官方 `mask_latent = 1 - mask_condition`（白=重画）→ **1 = 保留原图**。
填 1 + 空的 masked-image = 让模型"保留这张空图" → 输出全透明
（实测 RGBA 不透明占比 **0.0%**）。

**教训：像素差这个指标会骗人**。填 1 时像素差反而更大（40→80），
看着像"控制力翻倍"，实际是画面在往空白塌。以后判据要看「不透明占比」
和肉眼，不能只看像素差。

### ③ prompt 必须描述完整画面（决胜的一环）

官方建议 "write a prompt that describes the **whole** target image"。

只写 "a 2D game character sprite, centered, plain background" 时，模型不知道
画什么，**直接照抄骨架**：0.8 出粗黑线条人、0.6 出淡灰线条人，完全没有角色。

换成描述性 prompt 后同一个 seed 立刻出完整角色：
```
a female warrior in blue leather armor, standing with legs wide apart,
arms hanging at her sides, facing viewer, full body, 2D game character sprite,
flat cel shading, clean lineart, detailed
```

**这是整条链上最反直觉的一点**：一直以为在调控制强度，其实是在调 prompt。

### 顺带确认的事

- `_pack_latents` 是 `view(B,C,HW).transpose(1,2)`，2.1 不需要 patchify ✓
- joint 序列里图像 token **是**连续后缀（2304/2373，diff 全 1）→ 前缀切片能用，
  但仍优先用 `image_pad_mask` 精确散射（从 transformer 入参 `img_mask` 复算，
  照抄 diffusers 的 `repeat_interleave(img_mask[0], where(img_mask,4,1)[0])`）
- 透明底（`--transparent`）顺带解决"背景被条件图污染成米黄"
- VideoX-Fun 里 control 链是**完全独立**的 16 层堆叠，`x_joint` 只在 block 0
  用一次；skip 加到**整条 joint（含 text）**，不排除文本 token

### 最终可用配置

| 步数 | scale | 结果 |
|---|---|---|
| **24** | **0.45** | 完整角色 + 姿态逐点贴合 + 透明底，画质略软 |
| 8（Lightning） | 0.6 | 同样贴骨架，头部细节更弱 |

`tools/verify_controlnet_union.py` 的默认值已改成 24 步 / 0.45 / 描述性 prompt。

## 三转：VNCCS PoseStudio —— 人家根本不用 ControlNet（2026-10-31 01:2x）

用户指出「画风变了、多了条腿」，并给了 RunComfy 那个号称"完美保持角色一致性"
的工作流链接。去查了 `MIUProject/VNCCS_PoseStudio_QI2.1` 仓库里的
**官方 ComfyUI 工作流 JSON**（比网页描述精确得多），节点清单 14 个，
**一个 ControlNet 节点都没有**：

```
LoadImage(角色, image_2) ─┐
VNCCS_PoseStudio(骨架, image_1) ─┤
                                 ├→ TextEncodeQwenImage21 → KSampler
LoraLoaderModelOnly(VNCCS_QI2_PoseStudioV1, 1.0) ─┘
```

固定指令（逐字）：
`replace the pose of <image 2> with the pose of <image 1>. keep the character of <image 2>`
KSampler: steps=25, cfg=1, euler, simple；negative=""；输出尺寸取自**角色图**。

### 实现与结果
LoRA 152MB（ComfyUI 格式，rank 32，384 张量）→ `convert_lora.py` 转 diffusers
→ `load_lora_weights`。脚本 `tools/verify_vnccs_pose.py`。

| | ControlNet Union | VNCCS LoRA |
|---|---|---|
| 画风 | ❌ 灰白/塑料感 | ✅ 与参考图一致 |
| 头部 | ❌ 方形画布下丢失 | ✅ 完整清晰 |
| 肢体 | ⚠️ 偶发多腿 | ✅ 正常 |
| 服装/发型 | ⚠️ 部分丢失 | ✅ 皮甲缝线/腰带/护膝/靴扣/低马尾全保住 |
| 姿态 | ✅ 精确 | ⚠️ 能跟（交叉腿成立） |
| 耗时 | 17~51s | 18.6~30.4s |

### 两个关键细节（踩过才知道）
1. **画布要取骨架比例**，不是角色图。官方"取角色图"的前提是两者同比例；
   我们的角色图 768² 方形 + 骨架 512×768 竖版，取方形时骨架缩在中间，
   模型理解成"小幅度动作"，**交叉腿退化成双腿收窄**。取骨架比例
   （768×1152）后交叉腿立刻成立。
2. **骨架等比贴入不拉伸**。512×768 硬拉成 768² 会把腿压短，同样只跟一半。

### 教训
**先查别人的工作流 JSON，再动手实现。** 官方 JSON 里 14 个节点、一句固定指令、
一个 LoRA 强度值，比任何博客描述都准。我花了整晚在 ControlNet 的
mask/KV cache/画布/强度上打转，而正确答案是不用 ControlNet。
