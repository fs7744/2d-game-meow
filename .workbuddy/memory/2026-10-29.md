# 2026-10-29

## Qwen-Image 2.1 兼容性评估（咨询，未改代码）

结论：**架构不兼容，但产线有一半可直接复用**。

### 两侧栈的差异（决策依据）

| 项目当前假设 | Qwen-Image 2.1 实际 |
|---|---|
| UNet 4 通道（SD1.5/SDXL） | DiT transformer，32 层单流，视觉部分 7B |
| CLIP，77 token 上限 | Qwen3-VL 8B 文本编码器（约 17.5GB） |
| ControlNet（SD 权重） | 官方未提供，仅社区 ControlNet-Union 补丁 |
| IP-Adapter ViT-H | 原生多参考图，最多 10 张 |
| DPMSolver++ / LCM | FlowMatch Euler，参数名 `true_cfg_scale` |
| 靠 u2net 事后抠图 | VAE 原生输出 RGBA |

### 硬阻断点（不改代码会静默出错）

1. `engine.py:263 _arch_of` 只有 sd15/sdxl 二元判定 → Qwen 的 `_class_name` 是
   `QwenImage21Pipeline`（不含 "XL"）→ 被误判成 sd15。
2. `engine.py:225 _txt2img_ok` 读 `unet/config.json` → Qwen 布局是 `transformer/`，
   读不到 → 返回 True → **被登记进 `/models` 下拉，用户一选就崩**。最阴的一个。
3. `engine.py:148 _scheduler()` 强制 DPMSolverMultistepScheduler → Qwen 必须
   FlowMatchEulerDiscreteScheduler。
4. `generate.py:212 _text_kwargs` 传 `guidance_scale` → Qwen 是 `true_cfg_scale`；
   且 `"XL" in type(pipe).__name__` 会走进 SD1.5 分支去调 clip.py。
5. `engine.py:481/516` controlnet() / ipa_weight() 只认 SD 权重目录。

### 可直接复用（模型无关）

`generate.py` 里的 `_postprocess` 全套 + matte.py / pixelfy.py / postprocess.py /
quality.py / framescore.py / sheet.py / anim.py / pose.py / refcond.py / refprep.py
+ `workflows/video.py`（Wan2.2，与 Qwen 无关）。

### 现实约束

- 权重合计 33.1GB（transformer 14.2 + 文本编码器 17.5 + VAE 1.35）→ 24GB 卡
  必须 `enable_model_cpu_offload`，比 SDXL 慢。
- 许可：Qwen Research License，**仅非商用**（社区 ControlNet-Union 同）。
- 本机 diffusers 0.41.0 已有 `QwenImage21Pipeline`（含 `QwenImageLoraLoaderMixin`），
  但**没有** `QwenImage21ControlNetPipeline`。
- LoRA 机制可用，但必须是 Qwen 架构 LoRA，现有 13 个 SD LoRA 全部作废。
- `workflows/train.py` 只训 `UNet2DConditionModel` → 无法训 Qwen LoRA。
- `workflows/lora.py:172` 的 `supported = base in ("sd15","sdxl")` → 认不出 qwen。

### 建议路线

- **A（先做）**：Qwen 只当"打样 + 立绘"后端 —— 2K 透明原画 → 现成 pixelfy/
  postprocess → 像素精灵。改动最小，透明通道还能省掉 u2net。
- **B（中期）**：新增 `workflows/qwen_engine.py` 作第二引擎，不把 Qwen 塞进
  BASE_MODELS 的 sd15/sdxl 二元体系。W1 可通，W2 改"编辑"语义，W3/W5 靠社区
  ControlNet-Union，W4/WPC/WSS 放弃。
- **C（默认）**：不换。产线判据是 128 有效像素 / 32 色 / 单主体 / 前景占比
  5~60%，SDXL@768 单候选已 2.01s/可用帧；Qwen 的强项（2K 细节、中文排版、
  10 图合成）都不是这条产线的瓶颈。

## SDXL 动漫人物绘制能力

提交 `a279529`，已推送 origin/main。

### 起因（先测基线再动手）
SDXL base 画动漫人物：偏写实厚涂、手部/武器衔接糊、背景斑驳不干净。
根因是 **SDXL base 训练数据里动漫占比低**——基座能力上限，提示词救不了。

### 三件事
1. **动漫底模 `sdxl-anime`**（Illustrious XL v0.1，6.5GB）
   ModelScope: `OnomaAIResearch/Illustrious-xl-early-release-v0`
   → `models/checkpoints/sdxl-anime`（**注意 dest 要带 models/ 前缀**，
   第一版脚本写成 `checkpoints/sdxl-anime` 下到了仓库根）。
   自动登记成底模（架构按 _class_name 判为 sdxl）。
   备选：`AI-ModelScope/animagine-xl-3.1` 也能下。
   实测 vs base：纯正日系动漫、五官锐利、线条干净。
2. **`preset=anime`**（danbooru 契约），每条都有实测依据：
   - 质量词只要 `masterpiece, best quality`（堆更多是负优化）
   - 负向词要短（这些模型已排除低质量样本，堆词压制正常特征）
   - **风格必须显式给**（Illustrious v0.1 官方注明未做美学预调）：
     `flat colors, cel shading` → 赛璐璐平涂；`clean lineart` → 线条最锐利
   - **构图 tag 由用户给，契约不写死**：不给构图 tag 前景 83.5% 且四边贴边；
     加 `full body` 后 24.5% 无贴边
3. **修 SDXL clip_skip**（真 bug，见下）

### ⚠️ SDXL clip_skip 语义与 SD1.5 不同（最重要的一条）
diffusers SDXL encode_prompt：
```
if clip_skip is None:  embeds = hidden_states[-2]      # 默认 = penultimate
else:                  embeds = hidden_states[-(clip_skip + 2)]
```
**SDXL 默认就是倒数第二层** = 业界说的 "clip skip 2" = 动漫底模推荐档。
直接把用户 clip_skip=2 传进去 → 跳到 **-4 层** → 出图灰雾（std 38→19）。
换算：n ≤ 2 用默认；n > 2 传 `n-2`。
另一个坑：`do_classifier_free_guidance=False` 时 negative embeds 返回 **None**
→ 负面词全失效、CFG 退化成单向引导 → 同样灰雾。必须传 True。

### 推荐参数按底模覆盖（MODEL_RECOMMEND）
动漫底模：`1024² / 28 步 / CFG 8.0 / pixel=0 / palette=0 / clip_skip=2 / preset=anime`
**CFG 8.0 是实测选的**（网上流传 6.5）：6.5 下兽人五官松散、法师法杖顶端
结构混乱；8.0 下五官立体、武器造型完整。
pixel=0 因为动漫立绘要保画质，像素化是给精灵的。
前端 ModelRecommend 新增可选 clip_skip / preset，选中底模自动填表单。

### 顺带修的真 bug
测试夹具 `_fixture_frames()` 用 `ASSETS.glob` 只在 assets 根找，产物却在
`assets/projects/default/`（作用域隔离后的路径）→ 每次都重生成且仍报
「夹具帧生成失败」，10 个用例 ERROR。改 rglob 后正常，测试 308s → 191s。

### 验证
后端 375 + test_models 11 = 387 用例，前端 smoke 300/300。
三角色实测：单主体、无贴边、u2net 抠图成功、~4s / 10.5GB。

## 动漫转像素节点（wap）+ 像素色板污染修复

提交 `42ce027`，已推送 origin/main。

### 用户的判断是对的
「先出全身动漫图再转像素」实测确认有效。让 SD 直接画像素时，它在
「像素风要极简色块」和「人物结构要分辨率」之间妥协：

    直接画（像素 LoRA + pixel=6）  裁到腿、颜色连续渐变、768² 但有效像素 128
    动漫图 → 像素化                全身完整、1px 描边、原生 192²

### 头号根因：色板提取没排除透明像素
抠图后透明区 RGB 是**纯黑**（convert("RGB") 把 alpha=0 变 0,0,0），角色前景
常只占 16% → 色板被黑/白吃掉 84% 色位。实测一张立绘转像素后**只剩 12 色且
几乎全白**（色板前两位是 (2,2,2) 和 (238,238,238)）。修复后恢复 32 色。
**同一处 bug 也在序列帧替换里**（RGBA→RGB 再进 refine_batch），这就是之前
「色板只有 2 色」的原因。修复位置：pixelfy._collect_pixels 按 alpha 排除。

### 像素化三步增强（对照业界 photo-to-pixel 四阶段）
1. **量化前拉对比度**（prep_enhance）：不开时红披风暗红、金发土黄、整体发灰
2. 色板排除透明像素（见上）
3. **轮廓描边**（enhance_edges，业界叫 anti-melt）

描边三个坑：
- 描边色必须**从色板里选**，第一版乘 0.7 压暗 → 色数 32→45~49，破功
- **只描外轮廓**，内部结构边全描会把脸糊成灰块
- 色板档位稀疏时「最近档」= 原色，描边等于没画 → 改成「不超过目标亮度的
  最亮档，找不到更暗就用最暗色」

### 新节点 wap
两条用法：只写描述（先生成再转）/ 接现成图（直接转，不跑模型）。
默认 192²/32 色/对比度 1.0/轮廓描边开。
实测 6~15s / 10.5GB / 板外 0 / 单主体。

### 踩的坑
glob `archer2_*.png` 同时匹配到 `archer2_src_*.png`（1024² 未量化源图），
误判「产物空白」并浪费了一轮排查。**读产物时一定要排除 `_src` 和 `_raw`**。

### 验证
398 用例（387 + test_models 11）全绿，前端 smoke 300/300。

## Refiner「越修越糊」修复

提交 `9fbc439`（refiner）+ `29c2481`（UI 下拉/落点），已推送 origin/main。

### 两个真 bug（用户报「怎么精修反而糊惨了」）
**1) refiner cross-attn embeds 拼错维度语义（致命）**
- refiner UNet `cross_attention_dim = 1280` = **OpenCLIP bigG 的 hidden size**
  （同一个数不是巧合），要的是 text_encoder_2 的**完整 1280 维隐层**
- 老代码 `CLIP-L(768) + OpenCLIP 前 512 = 1280`：维度对、语义错 → refiner 按
  错误语义去噪 → 糊成灰雾 + 变色（白底线稿变灰底）
- 实测（768²/20步/起点0.8）：不精修 lap 1826；拼接版 480~727、像素差 28.4；
  完整 1280 维版 1582~1616、像素差 7.7

**2) 误用 `denoising_start`**
- 那是「两段式」参数（底模 denoising_end 提前停）；这里底模跑满，传 0.8
  等于「成品重新加噪到 80% 再只走 4 步」→ 必糊
- 正解：`strength = 1 − 精修起点`（0.8 → 0.2）

### 关键认知
- **refiner 不是画质增强**：768² lap 1826→1616、1024² 611→450，都略降
  （VAE 编解码有损，img2img 固有代价）。它只改质感，往写实拉。
- **不要传 latent 给 refiner**：会被当 PIL 图再预处理，实测方差只有 631。
- 界面「精修步数 20」≠ 跑 20 步：img2img 只执行 `int(steps×strength)`=4 步。
  已在 UI 标「0.80 ≈4 步」，meta 记 refiner_strength / refiner_steps_run。

### 测试（都验证过能红）
- embeds 必须**逐元素等于** OpenCLIP 隐层（只看维度拦不住，拼出来也是 1280）
- strength 换算与上下限
- 行为回归：精修后方差 ≥ 不精修的 70% 且像素差 ≤ 20
  → 临时改回拼接报「精修把图弄糊了：1061 → 463」
- **坑**：行为测试第一版用 8 步，strength 0.2 只剩 1 步，测不出来；改 20 步。

### UI 那批（29c2481）
- 产出风格下拉选不动 = **连调 setParam 互相覆盖**（展开源是渲染时闭包旧 p），
  加 setParams(patch) 一次提交；档位表抽到 web/src/genStyles.ts
- 新节点被 236px 浮动侧栏压住 → canvasBox()/centerWorld() 按可见区算
- smoke 之前只测「自定义」档（单字段）恰好绕过 bug，已补多字段用例

## 像素 LoRA 调研（PixelDream / RetroDiffusion）

提交 `54fe948`，已推送。权重没下到，但顺手的实测给出了两条硬结论。

### 两个模型的事实
- **PixelDream**（Civitai 1528534 / version 1729424）
  LoRA 217.9MB，**底模 Illustrious**，触发词 `pixeldream`，clip skip 2，
  训练 4425 步 / 10 epoch，4350 下载、Very Positive。
  许可 Illustrious License（FAIPL 1.0：允许微调/分发，禁闭源商用，衍生须开源）。
  另有同名 SD1.5 版（Civitai 1010793，288MB，CreativeML OpenRAIL-M，
  触发词是长句 "2d Pixel Art sprite style game character"）；
  学术项目 github.com/pr-2310/Pixel_Dream（自建 PixelAssets 数据集）。
- **RetroDiffusion**（hf-mirror: LostMedia/RetroDiffusion）
  **Public Domain Mark 1.0（可商用，最宽松）**，SD1.5 架构 0.9B，
  diffusers 目录 + fp16 变体（全套 2.03GB），自带专用 VAE，814 下载/月。
  现在是商业 SaaS（$0.03~0.18/张）+ API + MCP，真像素 16~384px。
- 附加发现：**Illustrious PixelArt Shader / Pixelizer**（Civitai 2451774，
  435MB，2026-03，trigger `pixelart`）——专为「把 Illustrious 插画转像素」训的，
  官方推荐 1024→缩 8x→nearest 放大，和项目 pixelfy 思路一致。

### 实测（3 prompt×2 seed，有效像素固定 128）
| 组 | 可交付 | 多主体 | 贴边 |
|---|---|---|---|
| sdxl + pixelart_xl | **83%** | 17% | 0% |
| sd15 + px_illustrious | 50% | 0% | 33% |
| sdxl-anime + pixelart_xl（自然语言契约） | 17% | 50% | **83%** |
| sdxl-anime + pixelart_xl（tag 契约） | 50% | 50% | 0% |

**结论 1：像素 LoRA 必须配训练时的底模。** 架构兼容 ≠ 能用——pixelart_xl
挂 Illustrious 不报错、能出图，但可交付率 83%→17%、贴边 83%。
**结论 2：Illustrious 不认自然语言构图词。** 换 danbooru tag 后贴边 83%→0%，
但可交付仍 50%（多主体 50%）。两个问题独立，都得满足。

### 下载渠道（实测，写进 tools/fetch_pixel_models.py）
- huggingface.co / civitai.com 直连 ProxyError
- hf-mirror.com 通但 ~40KB/s（2GB 要 13 小时）
- civitai.red API 通（能读元数据），下载 307 → b2.civitai.com 不通
- ModelScope 上两个都没有

## 两个 Illustrious 像素 LoRA 实测（权重到手后）

提交 `9bc9d57`。**结论与网上资料相反。**

### 硬边占比指标（本次新增，是像素画的真分水岭）
相邻像素色差 >32 的，占「所有非零色差」的比例。真像素画是双峰分布
（同色块内差 0、边界差很大），抗锯齿插画色差集中在中小值。
- 产线 64px 真精灵帧：**0.447**
- Illustrious 不挂 LoRA：0.198（可交付 83% 但只是"抗锯齿插画"）
- PixelDream：0.279
- **Pixelizer 1.0：0.407（可交付 89%）**

### PixelDream（Impish_Pixel_Art_）名不副实
Civitai 标 Pixel Art、4350 下载，但实测是**厚涂**（盔甲金属渐变、无网格）。
可交付 67%/多主体 17%。当插画 LoRA 可以，当像素不合格。
元数据 `ss_base_model_version=sdxl_base_v1-0` 但实际挂 sdxl-anime 更好。

### Pixelizer（Illustrious_PixelArt_Shader）才是正解
三个必须设置，缺一个就废：
1. 触发词 **`PixelArt_IL_One_Token_style_M_01`**（从 ss_tag_frequency 读，
   单 token），必须前置
2. **强度 1.0**（0.8 时只有 50% 可交付、还出过崩坏姿态；1.0 = 89%）
3. **契约用 anime（tag）**，不能用 pixel（自然语言）→ 贴边 0% vs 83%

横向：sd15+px_illustrious 50% | sdxl+pixelart_xl 83% | **本组合 89%（最好）**

### 两个教训
- **像素纯度上限由 LoRA 决定，不是后处理**：后处理只能把 0.198 的孔洞填满，
  拉不到 0.407。之前以为"直出+后处理就行"是错的。
- **假警报**：中途看到 u2net 把人物抠碎，复测是 0.8 强度下生成本身崩了。
  Pixelizer 产物 u2net / 色键控都能干净抠出。
- 坑：`probe_ill_pixel.py` 的 tag 必须带 prompt id，否则同 seed 多 prompt
  产出同前缀文件，事后取图会取错（踩过一次，把 slime 当 knight 看）。

## 产出风格「切不出去」修复

提交 `baa821d`，已推送。用户报「产出风格切换有问题」。

### 根因：LoRA 被当成所有档位的判据
`styleFromParams` 原来对**每一档**都比 LoRA。而档位切换只挂不摘 → 从
「像素精灵·Illustrious」（挂 Pixelizer）切到任何不带 LoRA 的档位：
preset/pixel/palette 都改了，但 lora 还挂着 → 反推无档可匹配 → 'custom'
→ 下拉弹回「自定义参数」；lora 一直不摘 → **之后每档都弹，进去出不来**。

同一处压着第二个 bug：**手动挂过 LoRA 的节点，所有不带 LoRA 的档位都选不进**
（「水墨国风」说明里就叫人配武侠 LoRA，照做反而选不进去）。

### 修法
1. **LoRA 只在档位自己声明时才作判据**：`x.lora === undefined || x.lora === lora`
2. **切走时摘掉档位自带的 LoRA**（`owned` 判断当前 lora 是不是上一档挂的）；
   用户手动选的 LoRA 不动

### 顺带
- 三个像素档位补 width/height 768（像素块相对尺寸算，从 1024 切回来会变
  170 有效像素，跟说明写的 128 对不上）
- `switchModel` 先校验 `models.includes(next)`：档位指定了没装的底模时
  以前会把 model 设成下拉里不存在的值（选择框变空、生成必失败）

### 测试（都验证过能红）
smoke 314 → 319/319，新增 5 条「切出去」断言。分别回退验证：
只退摘 LoRA → 1 红；两处都退回原样 → 3 红且下拉值都是 custom（与用户现象一致）。

### 教训
**「档位 = 一整套装备」就要有摘装备的逻辑**：只写挂不写摘，反推必然失配。
写「反推当前档位」这类函数时，可选字段（lora）在没声明的一方不能参与比较。

## Qwen-Image-2.1 正式接入（推翻当天早些时候的"不换"结论）

用户要求接入，实测后发现成本比预估低很多，直接做成了第三个底模。

### 关键事实（推翻旧评估的地方）
- 本机 diffusers 0.41 **已有** `QwenImage21Pipeline` + `QwenImage21Transformer2DModel`，
  transformers 5.21 已有 `Qwen3VLForConditionalGeneration` → 不用升依赖。
- **torchao 在本机不可用**（要求 torch≥2.11，本机 2.6）。旧评估里"text_encoder
  用 torchao fp8"这条路走不通，改成 bf16 + `enable_model_cpu_offload`，
  峰值仍只有 16.4GB，能进 24G 卡。
- 项目目录里**已带 transformer-fp8 缓存**（6.7G，键布局 `w_fp8`+`w_scale`），
  直接用，省掉 13.3G bf16 加载与量化时间。

### 实测数据（RTX 4090 24G，768²/20 步）
| 场景 | 耗时 | 峰值显存 |
|---|---|---|
| 文生图（冷启动含加载） | 50~61s | 16.4GB |
| 文生图（热） | 24s | 16.4GB |
| 指令改图（图生图） | 24~28s | 16.4GB |
| 原生透明底 | alpha 占 66~68% | 16.4GB |

### 四个必须记住的坑
1. **`true_cfg_scale` 必须配 negative_prompt**：管线判据是
   `do_true_cfg = true_cfg_scale > 1 and has_neg_prompt`，不传负向时 CFG 静默失效
   （cfg1 与 cfg4 输出逐字节相同）。恒传 `QWEN_NEG`。
2. **透明底要双段式声明**（官方原话，别改写）：
   头 `This is an RGBA image with transparency. ` + 尾
   ` The image has alpha channel and the background is transparent.`
3. **透明底不能同时用 SD 的像素契约**：`SPRITE_SUFFIX` 里的 "flat plain background"
   与"背景透明"矛盾，实测画出白底、alpha 不激活。透明场景改走短后缀。
4. **尺寸必须 16 的倍数**，否则 diffusers 只 warn 一句就静默改尺寸。

### 实现位置
- `engine.py`：`_arch_of` 加 qwen21 分支（**必须在 "XL" 判定之前**，否则
  `QwenImage21Pipeline` 不含 XL 会被判 sd15）；`_txt2img_ok` 加 transformer 布局特判；
  `_load_qwen21` / `_load_qwen_transformer`（fp8 逐键挂载，不能 load_state_dict——
  0 长度占位会报 size mismatch）；`_fp8_linear_cls`（weight 置空 Parameter 专供
  dtype 探针，否则时间步张量被转 fp8 溢出成 NaN）；RECOMMEND["qwen21"]。
- `generate.py`：`_qwen_txt2img` / `_qwen_img2img` / `_qwen_call` / `_qwen_prompt` /
  `sanitize_alpha`；`txt2img`/`img2img`/`image_to_pixel` 开头按 arch 分流。
- `app.py`：`/models` 新增 `caps`（transparent/instruction/lora），前端据此
  决定开关是否可勾。
- 前端：`transparent` 字段 + 图生成/转像素两处开关；开原生 alpha 时自动跳过抠图。

### 坑（前端）
- **白猫白底**：抠图（u2net）会把白色身体当背景一起切掉（实测身体被挖空）。
  这正是原生 alpha 的价值——`transparent=True` 时身体完整。
- LoRA 列表按架构过滤，Qwen 下天然为空，要加一句说明否则用户以为扫坏了。

### 调研：MultiAngle-T8 的结论（不能用于角色迁移/序列帧）
- 它是 ComfyUI 节点（非 diffusers），核心是 3D 相机重打光（TripoSplat + MakeHuman）。
- **没有 ControlNet**，作者明说"结构图是图像参考，不保证像专用控制模型一样严格"。
  我们的 W4/WPC 是 ControlNet 硬约束，换软引导会掉一大截。
- 自公布实测：主矩阵 32 张只有 7 张基本符合、2 张部分符合。序列帧要求帧帧对应，
  这个合格率直接判死。
- **唯一值得拿的是 AnyAngle LoRA**（`QI2.1_AnyAngle.safetensors`，
  `lilylilith/QI_2.1_AnyAngle`）：给 Qwen 做相机方位控制，可用于三视图立绘。
  优先级低——W4 + IP-Adapter 已覆盖精灵帧主要需求。

## 角色迁移失败的真因：JSON 没有 int/float 之分

用户报「角色迁移失败」，同时屏幕上有一条 float32 警告 —— **那条警告无关**
（`should be kept in float32: []` 是空列表，加载 ControlNet/UNet 时的常规提示）。

真错误：`TypeError: For single controlnet: controlnet_conditioning_scale must be type float`。

根因：diffusers 的 `check_inputs` 用 `isinstance(x, float)` 严格校验，
而 **JSON 不区分 int / float**——前端 JS 的 `1.0` 序列化出去就是 `1`，
Python 收到 `int 1`，`isinstance(1, float)` 为 False。
后端直调时写 `1.0`（Python float）所以不报，一经 HTTP 就必崩。
这个 bug 从角色迁移节点上线起就在，只是 diffusers 升到会严格检查的版本后才显形。

修法：`generate._floatify(kw)` 在 `_infer` 里单点收口（所有 ControlNet 调用都过它），
归一化 `controlnet_conditioning_scale / guidance_scale / strength / control_guidance_*`。
**clip_skip 不能进这个表**（整数语义，转 float 会进到切片 `-(clip_skip+2)`）。

## 底模改成节点级

用户要求「去掉统一选模型，每个节点单独选」。`GenParams.model` 存节点底模，
空串 = 跟随侧栏默认。侧栏改名「新节点默认底模」。

- `maxCandidates` / `canTransparent` 也必须按节点自己的底模算，不能读全局

- 切换只驱逐/套用该节点，别的节点不动

`Engine.evict_other_models(model, keep)`，在 txt2img/img2img/pose/inpaint 的
cache-miss 分支调用。判据用 `key.split(":")` **完全相等**，不能用子串
（`sd15` 是 `sd15-inpaint` 的前缀，子串会误杀正在用的）。

同时修了三个 `ensure_headroom(need_gb=2.0)` —— 预估值太小。
SD15 的 CN+IPA 实际要 6~7GB、SDXL 要 13GB。给 2GB 时若 qwen 占着 16GB，

## 角色迁移换路：Qwen-Image-2.1 双图条件（实测胜出）

用户反馈「SD1.5 / SDXL 角色迁移效果都不行」。实测对比后换了一条路：
**不用 ControlNet，用 Qwen 的多图条件**。

### 原理
SD 那条是**两个互相拉扯的约束**：IP-Adapter 抢身份、OpenPose ControlNet 抢姿态。
Qwen 的多图条件是**同一个 vision context**（`image=[图1, 图2]`），由模型自己
分配「谁是身份、谁是姿势」。

### 实现
- `generate._qwen_pose_clone`：动作参考图 → DWPose 骨架（复用 `refcond.build_condition`）
  → `refprep.prepare_reference(角色图)` → `image=[角色图, 骨架图]` + 固定英文指令。
- `_qwen_call` 的 `ref_image` 扩展成支持 list（多图）。
- `engine._ARCH_WORKFLOWS["qwen21"]` 加 `pose_clone`；前端节点下拉自动放出 Qwen。
- 角色迁移节点切 Qwen 时自动套 768²/28 步/cfg 4，并隐藏「姿态」「身份」滑块
  （ControlNet/IP-Adapter 专属，Qwen 路径没有强度旋钮）。

### 实测（4090 24G，768²/28 步/cfg4）
| 路线 | 耗时 | 峰值 | 结果 |
|---|---|---|---|
| Qwen-2.1 双图 | 72s | 19.3GB | 姿势与骨架**几乎逐点一致**，角色主色也继承 |
| SD1.5 CN+IPA | 7s | 5.3GB | 同一输入姿态基本没跟上 |

### 调研结论（AnyAngle / VNCCS PoseStudio / Fisher-Pose）
- 三个方案的关键都是「**骨架图**传递姿态」，不是模型内部参数。
- **AnyAngle LoRA** 是相机方位控制（配 3D 重建 + Blender），不是姿态迁移。
- **VNCCS PoseStudio LoRA**（`MIUProject/VNCCS_PoseStudio_QI2.1`）训练在 VNCCS
  自己的骨架格式上；我们出的是 DWPose/OpenPose 格式，格式不同则遵循度未知。
- **Fisher-Pose / PoseStudio** 是 ComfyUI 生态（浏览器 WebGL 3D），我们 diffusers
  进程内推理，移植等于重写。
- 结论：**不需要**为读骨架额外训 LoRA，Qwen-2.1 直接就能读懂 OpenPose 骨架图。
  真要提升是**交互层**（可拖关节的 2D 骨骼编辑器）。
- **本机 HF 下载受阻**：代理访问 huggingface.co / hf-mirror.com 持续 502
  (`Tunnel connection failed`)；ModelScope 直连可用但无这两个 LoRA 镜像。
- **硬约束路线**：pixelforge 有 `qwen-image-20b` + `qwen-image-controlnet-union`，
  但 union 是给 20B 训的（joint_attention_dim 3584），
  **2.1 的文本编码器是 4096，对不上，用不了**。接 20B 是另一条工程线。
