### 第十七轮：抠图后端对决（结论：不改默认，但要防呆）
提交 `f56f1e6` 已推送。164 用例全绿（153 / 104s + test_models 11 / 54s）。

**假设被推翻**：「像素画该用色键，因为 u2net 软边会磨圆像素角」——错。
`tools/ab_matte.py` 四个样本（768²）实测：
- 两个后端输出 alpha **都是二值**（mid-alpha 占比 0.0），软边问题根本不存在。
- 色键在像素 LoRA 的彩色/纹理底上几乎抠不动：cov 0.98 / 0.91；IoU 对 u2net 只有 0.13 / 0.33。
- 白袍 + 白底：色键把袍子当背景，主体碎成 **3 块**；u2net 完整（IoU 0.63）。
- W4 姿态帧（灰底）两者几乎一致（IoU 0.97），u2net 略干净。
→ `auto` 继续默认 u2net。**这张表就是不改的理由**，别再凭直觉重开。

**真正该修的是静默失败**：u2net 会整张抠空（草稿档 256²/8 步实测只剩 **0.44%** 前景），
下游贴边检测/主体计数/像素化全拿到空数据，最后交出一张空精灵且不报错。
`matte_auto` 现在按前景占比（1%~95%）判合理性，不合理就回退色键取更合理的那份；
`info` 出参回填 `backend`/`fallback`，`generate` 写进 meta 的 `matte_used`/`matte_fallback`。
强制 `color`/`u2net` 时不回退——显式选择必须可复现。

**`foreground_blobs` 是下界**：u2net 只分割「显著主体」，史莱姆图案墙实测只留 1 块，
所以 subjects=1 不代表干净，>1 基本确实脏。UI 文案已改成「抠图后还剩 N 块前景」。

### 第十九轮：拖本地图 / 图片节点 / 连线
提交 `919937a` 已推送。171 用例全绿（160/110s + models 11/53s），smoke 92→108 断言。

**POST /upload（新增端点）**：请求体是**原始字节**不是 multipart（少一个 python-multipart
依赖，浏览器 `fetch(url,{body:file})` 直接发）。校验：≤20MB、真能解码（坏文件 400）、

**图片节点（kind='image'）**：
- 拖本机图片进画布 → 图片节点；**拖到图生图节点上** → 直接成为那个节点的源。
- 右下角拖拽手柄改展示大小（屏幕 px 差要 /zoom 才是世界坐标）+ 「宽」输入框 60~900px，
  高度按原图比例。
- 源图解析顺序：节点自带 path > 上游 job.raw > 上游 job.path > 图片节点的 image.path。

**连线**：卡头右侧连接点拖出 → 落到图生图节点上即接为源；画布用 SVG 画贝塞尔曲线，
两端锚在**卡头 y+13**（线不穿过卡片内容）。实现要点：
- 命中判定用 `onPointerEnter` 收集 hoverId（不是 elementFromPoint）—— jsdom 里
  elementFromPoint 不可用，而 pointerover 事件能触发 React 的 onPointerEnter，
  这样 smoke 也能测。
- 连线状态放 ref（linkFrom/hoverRef），effect 只依赖 `linking` 布尔，否则每次
  pointermove 都会重建监听器。

**坑**：`hasSource` 之前只认 job.raw/job.path/node.source.path，图片节点当源时
全都不成立 → 生成按钮一直禁用。已补 `(sourceNode.kind==='image' && image.path)`。

**意外结论**：把**已像素化**的成品当图生图的源，出来仍是干净的像素精灵
（模型重画一遍再量化），没有把色块糊掉——之前的担心偏保守，raw 优先只是为了保细节。

**姿态检测的两个长期 bug（这次修的，影响 W4 闸门）**：
- **YOLOX 解码是坏的**：随包 `yolox_l.onnx` 输出**未解码**的 head 结果
  `((1,8400,85)`，前 4 列是网格坐标 + log 尺寸），anchor 布局与官方
  anchor-major（25200 条）不一致——8400 恰好等于格子数，说明每格只输出一个
  anchor。**没有可靠的解码方式**。原代码直接当像素坐标用 → 框是 `(-1,1,1,4)`
  垃圾，人体裁剪完全错位，姿态回归置信度全线 0.03~0.16。
  → 默认检测器改用 **torchvision FasterRCNN**（直接输出像素坐标，同图 18/18 关节全中）。
  torchvision 权重从 download.pytorch.org 自动下载（国内可达，约 70MB）。
- **检测不到人时静默出废图**：检测器 fallback 成整图框 → 姿态回归在整图上乱跑 →
  一堆坐标离谱的「关节」，看起来像成功了其实没用。加 `allow_fallback=False`
  严格模式，检测不到人直接报错。

**姿态模型只认得出真人**：版画/线稿（0.05~0.18 置信度）、像素画、卡通插画
全都识别不出来。测试素材必须是真人照片（仓库里放 `tests/fixtures/pose_ref_person.png`，
注意 `assets/` 整个被 gitignore，测试素材不能放那儿）。

**归一化取点的坑**：`min_points` 是**下限**不是上限。写反了会只取 10 个点，
肩膀/脖子全丢，骨架只剩头 + 一只手 + 两条腿。

**完美像素转换（wpx）**：新模块 `workflows/perfect_pixel.py`（FFT 网格检测 +
Sobel 吸附 + 每格采样，移植 pixelforge 的 perfectPixel MIT 版）
+ `workflows/pixelfy.py`（共享调色板 + alpha 二值 + 噪点清理）。
**移植时修了上游两个真实局限**（实测才发现，值得记住）：
- **梯度峰检测必须允许平台**：像素画的边界是锐边，Sobel 给出两个**等高**的
  相邻值（2832, 2832），严格的 `> ` 判断一个峰都找不到 → 网格检测对
  「本来就是像素画」的图反而失效。改成按等高平台切分、取中点。
- **阈值不能直接用 max**：锐边让两个相邻平台叠加，max 是单边界的两倍
  （5664 vs 2832），按 max 的 20% 算阈值会把所有边界全挡掉。改用平台
  高度的中位数当参考。

**网格吸附的容差**：吸附到 base 倍数时，若 `max(snapped, raw) > min(...)*1.5`
就放弃吸附（8→16 等于把像素密度砍半，细节全丢）。

**局部 AI 重绘（w5）**：新模块 `workflows/repaint.py`（纯 PIL+numpy 图像运算层）
+ `generate.ai_repaint`（裁剪「选区+上下文」→ img2img 跑 → 贴回）。
**w3 vs w5 的分工**：w3 走 SD1.5 专用 inpaint 权重（512 封顶、不能挂 LoRA）；
w5 用任意底模（能挂像素 LoRA、能用 SDXL）。**像素素材改局部必须用 w5。**

**三个真 bug（都是这次踩出来的，值得记住）**：
- **RGBA 图进 VAE 会 OOM**：4 通道让 UNet 首层激活爆炸，512² 直接报
  `Tried to allocate 36.00 GiB`。送模型前**必须 convert("RGB")**。
- **透明底不能直接 convert("RGB")**：透明区会变黑 → 模型把背景也当内容重画 →
  选区周围带一圈脏边。要用 `flatten_rgb()` 把透明区填白。
- **约束条款必须写英文且够短**：SD1.5 的 CLIP 只认英文；而且 77 token 是
  「用户提示 + 契约后缀 + 约束」共享的上限——约束 62 token 时全量 96，
  后半段被整段砍掉。约束压到 26 token（全量 47）才安全。

**strength 实测**（像素素材，25 步）：0.80 选区几乎没变（模型保留原样），
0.90 改动明显（默认值取这个），0.95+ 硬边会留矩形拼接痕（羽化 8px + 边界

## 角色迁移支持非真人 + 序列帧替换节点（wpc ref_mode / 新增 wss）

### 根因
角色迁移只认真人：人体检测（FasterRCNN，COCO person）→ RTMPose 骨架。

→ 游戏素材（像素角色、怪物、机甲、非人形）完全用不了。

### 解法
- `workflows/refcond.py`（新）：参考图 → ControlNet 条件图
  - `pose` 真人骨架 / `outline` 轮廓 / `auto`（先 pose，失败降级 outline 并记原因）
- `workflows/sheet.py`（新）：精灵图网格自动检测 + 切帧

- `generate.sprite_swap`（新，wss）：精灵图 → 逐帧换角色 → 按原网格重打包
  - `mode=generate` 跑模型换体型；`mode=recolor` 纯确定性换皮（不跑模型、零漂移）
- `pixelfy.recolor_by_luma`（新）：明度重映射换皮

### 三个关键实测结论（下次别再走弯路）
1. **轮廓条件不能只给边缘**。canny 是「白线画在黑底」，模型会把整屏当画布填满
   纹理 → 成品主体只剩 **3px**（参考 677px）。必须给**自制软边缘**（保留参考图
   灰度结构 + 边缘加重）→ 709px，轮廓 IoU 0.899。
2. **网格检测必须二维**。「找空行空列」4×1→10×3；「投影谷值」纵向 1×4→2×1；
   「单轴评分」因剑是独立连通域 4×1→6×1。最终判据：连通域不跨格 +
   各格主导连通域面积一致。认不出就要求手填，别默默切错。
3. **输出必须缩回原格子尺寸**（32~128px），768² 生成后缩；整段共享色板。

## 对照业界方案优化序列帧替换质量（wss/wpc）

提交 `842979e`，已推送 origin/main。

### 调研结论（2025-2026 业界横评）
- **帧间一致性是 AI 精灵图生成最难的未解问题**，所有工具都做不到 100%
- IP-Adapter + ControlNet 组合一致性只有 **70~80%**
- **同 seed 也不保证一致**（CLIP Vision 编码引入方差），逐帧漂移 20~30%
- 行业通用解法不是调参，是「**生成多张 + 逐张挑选 + 帧间对齐 + 锁定色板**」
- 「首帧定身份、后续帧继承」依赖视频模型（AnimateDiff 时序注意力），本项目没有

### 三个实质改进
1. **参考图预处理**（真 bug）：角色图直接 `convert("RGB")` 让透明区变黑，
   实测 66.5% 的像素角色图是纯黑背景 → CLIP Vision 把黑底当角色暗部。
   新增 `workflows/refprep.py`：填白 + 裁主体 + 居中留白 + 像素画最近邻。
2. **多候选择优**：每帧默认 2 个候选按分数挑，都不合格再补提。
   新增 `workflows/framescore.py`：silhouette(IoU) / identity / coverage /
   edge / drift —— **与主体类型无关**（w4 那套靠人体关节，对像素角色恒为 0）。
3. **按像素格采样**：以前 BOX 降采样会混色。改从生成尺寸一步按格采样，
   实测每格单色率 **4096/4096 = 100%**。

### 踩过的坑（重要）
自动判别「像素画 vs 低分辨率平涂插画」**本质信息不足**。试过 7 种判据
全都会在别的类型上误判：边缘跳变率（斜边漏判）/ 最近邻放大不变性（恒为真）/
色数+大色块（卡通也满足）/ 2×2 单色率（渐变图满足）/ 跳变周期性（水平渐变满足）/
亮度直方图中间层（绿色史莱姆落在中间层）/ 稀疏性（平涂卡通也少）。
→ 降级为启发式，判错后果只是插值方式不同。**别再在这上面花时间**。

### 验证
后端 295 用例全绿（原 273 + 22），前端 smoke 220/220。
端到端 4 帧 64px → 史莱姆 12.1s / 5.32GB；换皮 0.0s。

用户后续若要「更强的角色一致性」，正确方向是**训练角色 LoRA**
（业界实测 LoRA 一致性 0.84 vs IP-Adapter 0.78），本项目已有 LoRA 训练链路。

## AnimateDiff 显存优化 -41%

提交 `d1a42c1`，已推送 origin/main。

### 先剖析再动手（关键方法论）
写 probe_vram_breakdown.py 分阶段测峰值，发现峰值**不在 attention、不在权重，
而在 VAE 解码**：

    权重 5.62GB（UNet 2.49 + MotionAdapter 0.84 + CN 0.67 + IPA enc 1.18
                  + VAE 0.16 + TE 0.23）
    激活 4.24GB
    ├─ VAE 批量解码 4.00GB  ← 峰值
    └─ VAE 逐帧解码 0.60GB

### 三项优化（8帧 9.86→5.78GB / 16帧 14.09→7.10GB）
1. **VAE 逐帧解码**（省 2.9/5.8GB）：这条管线**没有** `enable_vae_slicing`
   （只有 diffusers 通用 pipeline 有），得直接 `pipe.vae.enable_slicing()`。
   质量差 0.1/255（数值精度级）。
2. **IP-Adapter 参考图编码器用完即退**（省 1.18GB）：image_encoder 是
   CLIP Vision，只编码一次参考图就闲置，diffusers 却让它常驻显存。
   **不能整块留 CPU**（编码跑 CPU 慢 52%）；要「调用时短暂上 GPU，用完退回」。
   输出**逐像素完全一致（差 0.0）**。共享 encoder 的多管线要按对象去重，
   否则包装器套包装器，encoder 退不下来。
3. **残缺帧补提复用同一管线**（省 3.23GB）：原来走 eng.pose_pipe() 会
   **再加载一整套** UNet/VAE/CN/IP-Adapter，权重完全重复。
   坑：**AnimateDiff 不能跑 num_frames=1**——motion module 输出畸形
   （area_ratio 5.5，膨胀 5 倍，IoU 0.17）；要跑 2 帧取第一帧（IoU 0.81+）。

### 顺带修的真实问题
- **Engine 权重池按 root 共享**（进程级 `_POOLS`）：多实例 = 同一份权重存
  多份。实测连续跑多个工作流峰值 14.9GB（单跑只 5.78GB）。
- **ensure_headroom() 显存压力自动驱逐**：引擎缓存管线但从不释放。
  判断依据必须用 `torch.cuda.memory_reserved()` 而非 `mem_get_info` 的
  物理空闲——后者不算 PyTorch 缓存的块，「物理空闲」≠「可用」。

### 显存档位
auto / low(384²) / medium(512²) / high(512²,≤32帧)。
**帧数永远不砍**（是用户的动画内容，砍了就是丢数据），只降分辨率，
实际值与原因写进 meta 的 vram_note。
显存随帧数**超线性**（8→16 涨 23%，16→32 涨 100%）——motion module 要在
整段序列上做时序注意力。估算用二次项拟合（偏差 3~18%）。

### 没用上的手段（别再试）
- `enable_attention_slicing()`：峰值无变化（瓶颈在 VAE 解码）
- `enable_model_cpu_offload()`：峰值反而**涨到 10.15GB**
- `vae.enable_tiling()`：512² 不触发
- image_encoder 整块留 CPU：慢 52%

### 验证
后端 311 用例全绿（原 298 + 13），前端 smoke 222/222。

## SDXL 精灵管线候选成本（稳态实测）
新增 tools/bench_sprite.py：预热1次+稳态2~3次取中位数，双口径显存（allocated/reserved），换算每可用帧成本 = t / (1-(1-p)^k)。
W1 每可用帧（p 来自 ab_base）：
- sd15 768 x1: 1.26s/4.55GB/p33% → 4.12s
- sd15 768 x2: 2.35s/6.68GB → 4.44s（批量反而更亏）
- sd15 768 x4: 4.55s/11.25GB → 5.82s
- sdxl 768 x1: 1.75s/10.95GB/p92% → 2.01s（最优）
- sdxl 1024 x1: 3.43s/14.13GB/p75% → 4.57s（1024 可交付率反而降，角色占比大更易顶边）

工具修了两个自伤 bug：成本公式 k*t/P 应为 t/P；后处理输入要用 __raw。
结论：精灵场景最优 = SDXL@768 单候选（2.01s/可用帧）；不要用 SDXL@1024 做精灵帧。

## 修 bug：正负 embeds 形状不一致（用户报）
报错：`prompt_embeds [1,77,768] != negative_prompt_embeds [1,154,768]`。
根因：clip.embeds() 判定"任一侧超长"后两侧都调 encode_long，但 encode_long 对短文本只出 1 段、长的出 2 段 → 各算各的。
修法：取两侧段数最大值 n，短的一侧补**空段**（BOS+EOS+pad），保证 CFG 相减形状一致。
新增 clip.split_chunks / _encode_chunk，encode_long 加 chunks 参数。
另加：超过 max_chunks 容量时 print warn（静默截断是这条链路的老毛病，不该再重复）。
实测：短正向 3 token + 长负向 289 token → 两侧 (1,154,768)，推理 OK；两侧都短仍走字符串路径（历史逐像素不变）。
测试：test_review_p1 +2 条（形状对齐 / 短文本仍走字符串），test_review_p1+test_quality 20 passed。

## 像素化/Refiner 都由用户在前端开关
- 像素化：显式复选框（以前只能靠"像素块填 0"关，太隐蔽→用户误填 64 得 8x8）。关时像素块输入框禁用并显示"关"；开启时旁边实时显示有效像素（768/6→128px），<64px 或色数<8 告警。
- Refiner：下载了魔搭 stabilityai/stable-diffusion-xl-refiner-1.0 的 diffusers 权重（8.3GB，13分钟）到 models/checkpoints/sdxl-refiner。
  - 底模自动发现要排除它（管线类 Img2Img，不是文生图底模）。
  - refiner UNet 没有 encoder_hid_proj → cross-attn 只吃 1280 维 = CLIP-L(768)+OpenCLIP前512；pooled 用 OpenCLIP 完整 1280。直接传 prompt 会报 (154x2048 and 1280x768)。
  - refiner 是 img2img 管线只接受图片：传 latent 会被当 PIL 图再编码 → 糊鬼影。
  - **关键结论：refiner 是"照片化"精修器**，喂动漫/像素图会变成"墙上挂的画"。写实图才值得开；文案已写明。
- 测试：test_review_fixes +2（refiner 不登记为底模 / has_refiner）、test_api +1（/models 带 refiner 字段）；smoke 300/300（+像素化开关 6 条 +refiner 7 条）。
- 另：SDXL 1024² + 像素块 8（同 128 有效像素）比 768²+块6 细节明显更好（对比图 assets/_res_cmp.png），代价：可交付率 92%→75%、耗时 1.5×。
