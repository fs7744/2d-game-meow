## 骨骼编辑器加「3D 感人形」显示层（09:55~10:10）

用户："骨架编辑那里能用 3d 那种人物形象吗？纯骨架分不清，结果依然保持现在骨架"

### 做法
编辑器加三种视图：**人形 / 线框 / 叠加**（默认叠加）。
人形用同一份 18 个关节现画（不是贴图）：
- 躯干 = 肩-腰-髋六边形（侧面自然收窄）
- 四肢 = 带锥度的四边形柱 + 高光线（暗示圆柱受光）
- 头 = 椭圆，横向半径随视角 `0.80·|cos a| + 0.66·|sin a|`
- 五官：正面两眼一嘴 / 侧面一只眼 / **背面无五官 + 发际线**
- **深度排序**（远→近画）：侧面两条腿一前一后，近的必须盖住远的，
  不排序就是纸片人

头部那 7 条边（鼻-颈、头骨四角、两耳到肩）在人形模式下**不画**（正好落在
脸上，把五官糊成一团彩色），关节点淡化到 0.45。**导出格式一个字没改**。

### 顺带发现：预设姿势是「大头短腿」
旧预设头占身高 22%、腿只占 34%。已按真人 8 头身做分段线性重映射
（头顶 0.02 / 鼻 0.075 / 颈 0.155 / 肩 0.18 / 髋 0.52 / 膝 0.72 / 踝 0.93）。
**这不只是观感**：导出的骨架比例失真，模型照着画出来的人也是 Q 版。
实测新比例下腿更长、身形更自然，姿态贴合度没变化。

### 失败不卡死（三道兜底）

根因：轮询里 `if (r.status !== 'fulfilled') return n` —— 查询失败就原样返回节点，
于是网络断一次 / 服务端重启，节点**永远**停在「生成中…」，按钮禁用。
- 提交：`fetch` 加 30 秒 `AbortController` 超时（否则请求挂住 = 永远排队中）。
- 轮询：连续 3 次失败（约 2 秒）→ 判定 failed，退出执行中。
- 看门狗：执行中超过 30 分钟 → 判定超时。
- 后端：worker 整个执行包 try（以前任务会永远停在 queued）；
  `/jobs/<id>` 404 时带明确文案「任务不存在或已被淘汰」。

### 踩到的坑

- **demo 模式要同步项目列表但不覆盖画布**：`?demo=1` 靠 URL 造节点，被服务端
  版本覆盖就没法截图了。但项目列表仍要同步（侧栏要能切）。
- **mock 的服务端状态必须每 boot 独立**：全局共享会污染后续用例——前一个用例
  往磁盘写了项目，后一个启动时拉到它，画布不再空，「新建出 X 节点」全错。
- **mock 的 URL 匹配顺序要紧**：`/projects/export` 也含 `/projects/`，
  必须先判掉，否则被「按 id 读项目」分支抢走。

## id 冲突处理（下午第三轮）

用户问「导入时 id 冲突怎么办」。查下来发现是**三个不同的冲突**，混在一起会互相掩盖。

### 根因：id 由浏览器生成

`p<时间戳36><序号36>`，两个标签页的序号都从 0 开始 → **同一毫秒建项目拿到
完全相同的 id**（实测 `pmdr5q6ns0`）。后保存的直接覆盖先保存的——
用户的画布无声消失，还以为保存成功了。

### 三类冲突与处理

| 冲突 | 处理 |
|---|---|
| 新建时 id 已被占用 | `PUT` 带 `create=true` → **409**，不覆盖 |
| 两个窗口编辑同一项目 | `PUT` 带 `expect_updated`（版本号）→ **409** |
| 导入到已存在的 id | 解包前检查目标目录 → **报错**，不写进去 |

**id 改由服务端分配**：`POST /projects/allocate`，随机后缀 + 存在性检查，
撞了就换。前端新建/导入/模板实例化/老存档迁移全部走它。

### 关键区分：版本号 vs 时间戳

- `expect_updated` = 「我读到的那个版本」（乐观锁比对基准）
- `updated` = 「本次保存的新时间戳」（写进磁盘，作为下一个版本号）

搞混的话本地一改就跟磁盘对不上 → 每次保存都误报冲突。
**`flushCurrent` 不能动 `updated`** —— 它是版本号不是修改时间（之前它冲成
`new Date().toISOString()`，会让乐观锁永远失效）。

### 踩到的坑

- **死锁（隐蔽！）**：`save_project` 持 `_WRITE_LOCK` 调 `_atomic_write`，
  后者内部又 `with _WRITE_LOCK` → 普通 Lock 重复获取自锁。
  表现为 pytest **卡住且不报错**（不是失败，是挂住）。
  修法：`_WRITE_LOCK` 改 `threading.RLock()`（可重入）。
- **mock 的冲突开关要在有节点的场景下测**：新建的项目是空画布，
  没有 textarea.prompt → 改不了 → 不触发自动保存 → 提示不出现。
  要先切回有节点的项目。
- 冲突提示渲染在 `.toast` 里（`uploadMsg || notice`），断言选择器别写错。

### 验证

- 后端 test_project_store：17 → **27 条**（新增 id 唯一性、撞 id 409、
  乐观锁、导入冲突）
- 前端 smoke：336 → **344/344**（新增 id 分配、冲突提示 4 条）
- 真实 HTTP：分配 5 个 id 互不相同 → 撞 id 409 且第一个还在 →
  A 保存后 B 用旧版本号 409 且 A 的改动保住 → 正常更新 200

## 「透明底怎么这么多白的」（commit da61002）

### 根因链（可复现，不是猜的）

用户勾了透明底 + 色数 16 → 出图左右两大块实心白。取他项目里的 `*_raw.png` 一量：

```
alpha: <16 2.8% | 16~127 14.7% | 128~240 68.1% | >240 14.4%
```

1. **Qwen 这次画出的 alpha 是雾**（68% 停在中间值）——提示词与透明声明打架时就会这样；
2. `postprocess.quantize_palette()` 里 `alpha.point(lambda a: 255 if a > 127 else 0)`
   把 68.1% + 14.4% 全推到 255 → 不透明率 14.4% → **82.5%**，RGB 又被量化成白。

用 raw 跑旧链路，不透明率精确复现 82.5%，与截图一致。

### 修法

`_postprocess(..., transparent=True)`：先 `matte.alpha_trust()` 判 alpha 可不可信
（**a0 ≥ 10% 且 mid ≤ 12%** 才可信，阈值在 matte.py:123）：

- 可信 → 复用（重抠会咬掉白毛/白鞋）
- 不可信 → `matte_auto` 重抠，再进量化

w1/w2 的调用从 `matte=(matte and not transparent)` 改成传 `transparent=`，
判断只留一处。meta 加 `alpha_recut` / `alpha_mid`。

结果：同一张 raw，不透明 82.5% → 14.7%，角色本体完整。

### Qwen 的 CFG 不是 SD 的 CFG

用户填了 **7.5**（SD 的习惯值）。Qwen 里 >1 就是「真 CFG」（每步跑两遍 transformer），
7 属于强引导、容易过饱和 + 背景起雾。他的图生成耗时 63.22s，cfg=1 时约一半。
已在 hint 里写明「别照 SD 习惯填 7，从 2~4 试起」。
同理 1024² + 28 步也不是推荐组合（768²/16 步单帧 ~10s，他用了 63s）。

## 「人物边缘明显有问题」= 显示层的 pixelated（89c3717）

用户第三次报边缘问题。这次不是图脏，是**CSS 用错了采样方式**：

`.preview img { image-rendering: pixelated }`，而节点里的图是 768/1024、
卡片 260~620 宽 → **永远是缩小**。最近邻缩小会把边缘「半透明 + 背景白」的
像素整颗保留 → 一圈白点 + 锯齿毛刺。

PIL 等价对照（1024→400）：NEAREST 一圈白点、断裂；LANCZOS 干净。差异一眼可见。

### 修法：按尺寸判，不是在 CSS 里一刀切

不能删掉 pixelated —— **128px 的像素化成品在卡片里是放大**，那时必须最近邻。
判据：`naturalWidth <= clientWidth ? pixelated : auto`。

用**捕获阶段的 load 事件**统一处理（img 的 load 不冒泡但能被捕获），
避免在十几处 `<img>` 上挂 onLoad，也不会漏掉以后新增的图。

节点最大宽 620 < 768 → 大图恒 auto、小图恒 pixelated，拖宽不改变结论。

### 教训：报"边缘脏"先分清三层

1. **显示**（image-rendering / 缩放方式）—— 用户第一眼看到的就是这层
2. **alpha 边界**（阈值化 / 抠图 mask 胖瘦）
3. **RGB 污染**（边缘像素混了背景色）

这次是第 1 层。前两次（白块、白边）分别是第 2 层。**先看看是不是显示问题，
别一上来就去改图像算法。** 判据：把图按显示尺寸用 LANCZOS 缩一遍，
如果白点消失 → 就是显示层的锅。

### 做过的负结果（别再重复）

inpaint 去污染（alpha=255 且 RGB 偏白且孤立的像素用邻域填）：命中 513/107017，
1:1 放大对比改善很小，误伤白鞋/白毛风险不小。不做。

## 「导出超时」的真凶是 MIME + 改成官方 3D 人偶编辑器（commit cbc7ba2）

### 超时根因：`.mjs` 的 MIME，不是加载慢

用户报「导出超时」。查下来**不是网格慢，是官方渲染器压根没加载**：

- 本机 Python 的 `mimetypes` **不认识 `.mjs`** → `guess_type('a.mjs')` 返回
  `text/plain`（`.js` 正常返回 `application/javascript`）
- 浏览器对 `<script type="module">` **强制 MIME 校验**，text/plain 直接拒绝
- → 页面永远停在「加载中…」，父页只能空等到超时

**排查手法（可复用）**：先看 `curl -I <静态资源>` 的 Content-Type。
Starlette 的 StaticFiles 用 mimetypes.guess_type，不认识扩展名就退化成 text/plain。

修法（两处，互补）：
1. `entry.mjs` → `entry.js`、`morph_runtime.mjs` → `morph_runtime.js`
   —— **.js 的 MIME 本来就对，不依赖重启后端**（用户的服务是常驻的）
2. `app.py` 里 `mimetypes.add_type('text/javascript', '.mjs')` —— 双保险，
   官方还有一批 .mjs（animation/characters/imports/video）

配套：宿主页面加 **inline script 早期错误捕获**（截 window error 的 SCRIPT 目标）
——模块没加载时模块内部的 try/catch 根本不执行，只能在宿主截，立刻上报给父页。
等待上限 60 → 180 秒（37MB 网格首次十几秒）。
