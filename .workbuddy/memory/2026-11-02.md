# 2026-11-02

## 透明底白边 + 不替用户抠图（commit f1b90be / ada8226）

用户两轮反馈：
1.「你看这边缘这头发，你肯定抠图了」—— 透明底边缘一圈白雾；
2.「我没选抠图，你为啥要主动扣？」—— 确实有代码在替他抠。

### 一、白边：保留过渡带 ≠ 保留白色

模型出的透明底，RGB 是**白底预乘**的：`C_obs = 前景*α + 白色*(1-α)`。
实测 Qwen 图：过渡带（16≤α≤240）亮度 **237.8**，实心区 206.4，
**87% 的过渡像素接近纯白**。只保留过渡带 = 连白色一起保留 → 深色背景上一圈白边。

解法是标准 **unpremultiply**（`generate._defringe_white_matte`）：
```
C_fg = (C_obs - 255*(1-α)) / max(α, 0.25)
```
- `max(α, 0.25)` 兜底：α 很小时除法会过曝。
- **只在检测到白污染时才动**（过渡带比实心区亮 > 25），否则模型给对了颜色反而被压暗。
- 过渡带样本 < 64 个像素时不动手（防零星抗锯齿点被误判）。

**关键坑**：`alpha_trust` 通过（`alpha_reused=True`）时原代码直接 return，
连 defringe 都跳过 —— 而 `alpha_trust` **只看 alpha 数值分布，不看 RGB**。
真机上这张出问题的图恰恰是 `alpha_reused=True`。所以「复用 alpha」≠「RGB 也干净」，
复用时要单独过 defringe。

真机效果：过渡带亮度 237.8→178.4，纯白占比 87.1%→44.8%；放大看手臂外轮廓，
修复前的浅白光晕没了。

### 二、"没选抠图却主动抠"：四处

| 位置 | 原来 |
|---|---|
| `_postprocess` 第 3 分支（alpha 全雾） | 自己调 `matte_auto`（u2net）—— 就是它啃头发边缘 |
| `pipeline.PIPELINE_DEFAULTS` | `matte: True` |
| 前端一键出全套 | 硬编码 `matte: true`，用户没得选 |
| `app.py` 6 个请求模型 | `matte: bool = True` |

全改默认 False。`_postprocess` 整张雾时只做最小清理 + 打 `alpha_missing` 标记。

### 三、配套：默认改走原生透明，否则出绿底

只关 matte 会得到绿底图，所以：
- `charactergen.normalize_background_color` 默认 `Green` → `Transparent`
- `posegen`/`emotiongen`：`transparent` 按「显式参数 > 背景色 > 默认透明」，
  背景默认从 `"Green"` 改成空

### 记住
- **「抠图」必须是用户显式选择**。默认 True 的地方要一个个揪出来：
  `_postprocess`、`PIPELINE_DEFAULTS`、前端硬编码、`app.py` 请求模型。
- 判断"有没有抠图"看 meta 的 `matte` 字段，不要猜。
- 透明底的 RGB 是白底预乘的，任何"保留半透明边缘"的处理都必须配 defringe。

## 白边的真凶：色数量化会硬切 alpha（用户问「是不是你限制色数了」）

用户猜对了。`postprocess.quantize_palette` 里有一行
`out.putalpha(alpha.point(lambda a: 255 if a > 127 else 0))`，把 alpha 硬切成
0/255。模型透明图的白底预乘过渡带（RGB 220~240、α 中段）因此变成**完全不
透明的近白像素** —— 深色背景上就是一圈实心白边，发梢同时被削成硬色块。

实测（真产物 768×1024，pixel=0/palette=32 走旧逻辑）：半透明像素 23356 → 0，
其中大量被强行变不透明；合成深色背景看，旧图头顶和右发沿有浅白描边、发丝
成锯齿色块，新图边缘平滑、发丝完整。

更隐蔽的是判据：`hard_edge = pixel > 1 or palette > 0` —— 用户只填了「色数
32」，系统就当他在做像素化，连契约词都换成 pixel art。这就是"没勾像素化却
有像素感 + 白边"的同一个开关。

改法：
- `quantize_palette(..., binary_alpha=False)` 默认保留原 alpha；
- `hard_edge` / 量化 / 契约词 / 开运算 / pre_pixel 全部只看 `pixel > 1`；
- 只填色数不再改变任何行为（`test_palette_alone_is_not_pixelation` 钉住）；
- UI 按业界做法删掉色数与像素块两个手填入口，「自定义参数」降级为旧存档
  只读回显（disabled），smoke 里改成断言"不许再暴露回去"。

顺带修了 `tests/test_qwen_workflows.py` 里 `fake_qwen` 缺 `raw` 参数
（上一轮 raw_output 改动漏的），以及 `test_quantize_alpha_is_binary` 这条
把错误行为钉死的测试。

## 图片预览加缩放/平移（灯箱 v2）

用户要"图片预览加放大缩小，方便看细节"。原来 Lightbox 只能等比塞进窗口，
而且**恒开 `image-rendering: pixelated`**（1024 图缩到 800 宽显示全是锯齿）。

做法（照业界图片查看器）：
- 滚轮以光标为中心缩放，公式 `t' = m - p·zoom'`（p 是光标下的图像坐标）；
  放大后拖动平移、clamp 到图边；
- 工具条 − % + 适应 1:1，键盘 + − 0 1、Esc，双击「适应 ↔ 4 倍」；
- **zoom 语义 = 真实像素比**，100% 就是 1:1，初始 = 适应窗口；
- `image-rendering` 跟着 zoom 走：≥1 最近邻、<1 平滑（本项目的老规矩）；
- 图下铺棋盘格：透明 PNG 在纯黑上看不出边界，也看不出白边/脏边。

两个坑：
- **React 的 onWheel 是被动监听**，里面 preventDefault 不生效 → 必须
  `addEventListener('wheel', fn, { passive: false })`，否则页面跟着滚。
- 灯箱必须 **Portal 到 body**：角色中心的 `.sprite-stage` 是 overflow:hidden，
  就地渲染会被裁（与节点卡片里提示词弹窗同一个坑）。

顺带把角色中心的素材帧也能点开看（SpritePreview 里挂灯箱）。
测试在 smoke 的 18) 与素材翻看场景，共 13 条断言。

## 两个真机反馈的 bug（转像素失败 / 拖预览就关）

**转像素失败**：`App.tsx` 提交前的 `init` 判定列表里**只写了注释、漏了
topixel** —— 节点能连线、界面还提示"有源图可留空提示词"，但 `init` 永远是
undefined，后端只收到空 prompt → 「需要 prompt 或 init_image 之一」。
现在 topixel 也走 `sourcePathOf`，源图缺失不拦（它本来就可选，没图就用提示词先出图）。
教训：**注释说"例外"不等于代码里处理了**；这条链路以前一条冒烟用例都没有
（现在补了 7 条，钉住 `init_image` 必须是字符串）。

**灯箱一拖就关**：舞台里的 click 冒泡到 `.lightbox` 的 onClose（"点背景关闭"），
拖动松手后浏览器补的 click 也算。修法：舞台 onClick 先 `stopPropagation`，
再用 `justDragged` 标记把拖拽收尾的那次 click 排除（只有真点空白才关）。

排查方法记一下：后端在 8000 跑着时，直接 `curl -X POST /generate` 复现
更快——同一张图 + 同参数返回 done，就能确定问题在前端而不是后处理。

## 人偶节点：嵌入模式从来没生效（同一块地方两套工具条）

现象（用户截图）：卡片里 iframe 内一套「朝向 / 重置视角 / 导出人偶图」+ 提示行，
宿主又一套「姿势库 / 朝向 / 机位 / 三个按钮 / 导出」；iframe 里那个导出点了没反应；
宿主按钮是竖排的「视/角」「站/立」「从/图」。

根因：
1. `studio.html` 里 `html.embed #bar/#hint/#out { display:none }` 一直写着，
   `entry.js` 也把 `?embed=1` 读成了 `EMBED`，**但没有任何一行给 `<html>`
   加 `embed` class** → 整套规则是死的。加 class 要放 `<head>` 内联同步执行，
   放 module 里会先闪一下工具条。前面加过的冒烟断言只验了 iframe 的 src，
   所以这个漏洞一直没被抓到；现在直接断言 studio.html 文本里有 classList.add。
2. `.mini` 是 28×28 的图标按钮（memory 里早就记过），两字中文必竖排；
   `.mini.wide` 是 `width:100%`，和三个小按钮挤同一 flex 行会被压成窄长条
   （看着像输入框）。修法：`.pose-editor .mini { width:auto; white-space:nowrap }`
   + `.pose-actions { flex-wrap:wrap }` + 导出按钮 `flex: 1 1 100%`。

文案也顺手改准：视角→重置视角、站立→重置姿势、从图片→从图片提姿势。

## 图片提姿势崩掉：COCO→OpenPose 映射写错一格（2026-11-02）

用户拿瑜伽/舞蹈照（侧弯 + 单腿站立 + 单腿抬起）试「从图片提姿势」，
人偶崩成麻花。不是模型问题，是 `workflows/pose.py` 的 `COCO_TO_OP`
把 `13` 写成了 `R_ANK`（应为 `L_ANK`）→ OP 10 和 OP 13 都取 COCO 16，
**左脚踝从来没被用上**。直立站姿两脚挨得近看不出来，抬腿姿势就叠在同一点。
实测修前两脚踝距离 0.000、修后 0.530；2D 骨架叠回原图 18 点全对。

教训：**这类"两路取同一个源"的错误只有极端样例能暴露**。加的是纯常量
双射检查（不跑模型），比端到端测试便宜得多。

**修完也只是"不再是麻花"**：官方 `convertOpenPoseToPose`（pose_studio/
imports/openpose.js）假设画面正视、2D 点做两骨 IK，**没有深度先验**——
侧身悬空/身体轴线倾斜的姿势会被解释成"弯腰+屈膝"。这是 2D→3D 的固有歧义，
业界（Rokoko / Plask / DeepMotion）都用 3D 姿态模型（SMPL-X / HybrIK /
MediaPipe Pose Landmarker 出带 z 的点）再 retarget 到骨骼。要根治得引
3D 前后文，光调 2D 点阈值没用。

## 从图片提姿势接入 MediaPipe 3D（2026-11-02）

修完左脚踝映射后，人偶不再麻花但仍会**躺倒**。根因不是点错，是官方
`convertOpenPoseToPose` **只有 2D**：它从"髋线在画面里的角度"反推骨盆倾斜，
侧身照片的两髋投影只隔身高 1.5% → 判出 -81° → 整个人偶绕 Z 转倒。

方案：MediaPipe Pose Landmarker（`pose_landmarker_full.task` **9.4MB**，
Apache-2.0）给 `pose_world_landmarks`（米制 3D、髋原点、y 向下、z 朝相机为负）：

1. 双肩连线在 xz 平面的角度 = 躯干 yaw（这张图 61.9°）；
2. 绕 Y 转正；
3. 取 (x,y) **等比**投影（实测髋线 0.015 → 0.156，角度 -81° → -31°）。
4. 前端必须把 `modelRotation`/`cameraYRotation` **归零**（`joints` 消息带
   `reprojected`），否则转换器会拿投影压扁的髋线再判一次，人偶又躺。

对比过的替代方案（别再来一遍）：
- **SMPL-X**：`SMPLX_NEUTRAL.npz` ≈228MB，且 **MPI 注册制、仅非商业、禁止分发**；
- **HybrIK**：权重数百 MB~1GB + PyTorch3D（Windows 编译坑）；
- 所以先上 MediaPipe。精度不如 DWPose（PDJ 91.8%），但它是**唯一给深度的**。

遗留：肢体交叠处（手抓脚）3D 精度不够，实测左手腕离右脚踝 0.2 个身高，
需要用户在人偶上微调。要更准只能上 SMPL 系（先解决许可）。
