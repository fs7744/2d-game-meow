## 0. 结论摘要

这个项目在**确定性后处理**和**实验方法论**上做得比多数开源同题工具好（网格对齐 100% 每格单色、
选区外逐像素不变、每条优化都有 A/B 数据）。真正的短板不在"少做了什么功能"，而在三处：

| # | 判断 | 证据 | 影响 |
|---|---|---|---|
| 1 | **底模是最弱一环，不是 SD1.5 架构的问题** | `models/checkpoints/sd15` 是 runwayml **base v1.5**（diffusers 0.6.0 导出、带 safety_checker、下载源 `AI-ModelScope/stable-diffusion-v1-5`） | README 里"SD1.5 画不出刀/铠甲"的结论，实际归因于**基座而非架构**。换同架构社区微调，显存/速度/授权全不变 |
| 2 | **显存缓存机制实质失效（逻辑写反）** | `engine.py:468-499`，已复现：`ensure_headroom(2.0)` 会把**全部**缓存管线驱逐 | 每次 wss/wpc 都重载 UNet（数秒），而 `_ctrl` 不随驱逐释放 → 权重双份 |
| 3 | **LoRA 状态是"池级"而非"管线级"，会静默丢 LoRA** | `engine.py:437-464`，已复现：第二条管线同 LoRA 直接跳过加载 | W1 用了像素 LoRA，接着跑 W4/WSS → 风格丢失且无告警 |

另有 6 项中等问题（WPC/WSS 硬编码 sd15、WSS 默认路径 preset 双拼、质量闸门评错了对象、
70 token 截断丢掉契约尾部、单卡利用率 11%、训练与生成抢卡）见第 3、4 节。

## 1. 功能全景 vs 业界

| 能力 | 本项目实现 | 业界成熟做法 | 差距 |
|---|---|---|---|
| 文生图 / 图生图 | SD1.5/SDXL，DPM++ 2M Karras 30 步 | 社区微调基座 + 少步蒸馏 + 高清修复两段式 | **大**（基座 + 步数策略） |
| 局部重绘 | w3 专用 inpaint 权重；w5 裁剪→img2img→贴回 | Differential Diffusion（软蒙版混合）/ Flux Fill / LaMa 修补 | 中（w5 缺软混合，硬贴回靠羽化补） |
| 角色一致性 | IP-Adapter(ViT-H) 单张参考图 | IP-Adapter FaceID / InstantID / PuLID；多图参考取平均 embeds | 中 |
| 姿态驱动 | YOLOX/torchvision + RTMPose → OpenPose-18 + CN | DWPose + OpenPose 图，**512 训练分辨率**上用 512 推理再高清修复 | 小（但分辨率用法有偏差，见 Q6） |
| 序列一致性 | AnimateDiff v1-5-2（2023）+ 残缺帧补提 | 视频底座（Wan/VACE）直接出序列；AnimateDiff-Lightning / SparseCtrl | 中（项目里**已经有** Wan2.2，未接动画线） |
| 像素化 | FFT 网格检测 + Sobel 吸附 + 每格中位色，100% 单色率 | 多数工具只做 BOX 降采样 | **优**（这一项领先） |
| 抠图 | isnet-general-use（2022）+ 色键回退 | BiRefNet（2024）/ RMBG-2.0 | 中 |
| 帧质量闸门 | 关节数/占比/贴边/漂移 + 多候选择优 | best-of-N + reward model | **优**（思路正确，落点有偏差） |
| 导出 | Godot tres/tscn + 通用 JSON + GIF/APNG + zip | 同 | 齐备 |
| 服务 | FastAPI + 单 worker FIFO + jsonl 索引 | SQLite 索引 + 显式队列/取消 | 小（但索引与任务表会无限增长） |

结论：**功能面不缺**，缺的是"同一个功能用更对的方式实现"。

## 2. 生成质量

### Q1（最高优先）底模是 base v1.5 —— 这是"画质差"的主因

```
models/checkpoints/sd15/model_index.json
  "_diffusers_version": "0.6.0"        ← 原始 1.5 导出
  "safety_checker": [...]              ← 社区微调几乎都剥掉了
tools/fetch_modelscope.py:73  "AI-ModelScope/stable-diffusion-v1-5"
```

原始 v1.5 只见过 LAION 的通用图文对，"拟人角色 + 武器 + 铠甲"这种复合概念本来就在它的能力边界外。
README 把这归因为"SD1.5 的能力上限"，于是引入了 SDXL（慢 3-4×、显存 2×、授权受限）——**代价付得没必要**。

社区 SD1.5 微调（AnythingV5 / DreamShaper 8 / majicMIX / 像素向基座）与原版**架构、显存、步数完全一致**，
只是权重不同。同一份 TDM 评测表里，DreamShaper 在 25 步时 HPS 30.41 已高于原版 v1.5 的 30.03，
而在"动漫/游戏素材"这类域外题材上差距远大于 HPS 所反映的均值。

**建议**：不要靠肉眼判断，用项目里现成的 `tools/ab_quality.py` 扩成基座 A/B——
6~8 条产线 prompt × 3 seed × 3 个基座，指标直接用 `framescore`（剪影/身份/贴边/主体数）+ 每格单色率 + 人工 5 分制。
判据：同样的 `pixel=6 / palette=32` 后处理后，"单主体率"和"武器/铠甲出现率"是否显著上升。

> 这一条如果成立，收益大于后面所有优化之和，且**不增加任何显存与耗时**。

### Q2 77 token 截断正在真实地吃掉质量

`presets.py` 里 `WUXIA_NEG` 自己注明"实测这串写到 113 token 尾部全被静默丢弃"，
`fit()` 的做法是**直接砍掉尾部**。也就是说：武侠契约里"4 质量兜底"那几段从来没生效过。

SD1.5 的 UNet 交叉注意力对序列长度不敏感，A1111 的"CLIP 77→154"就是分段编码后拼接。
项目里已经有 `workflows/clip.py` 在自算 embeds（为了绕开 diffusers 的 clip_skip bug），
**改成按 77 分段编码再 concat 是增量很小的改动**：

```
embeds = cat([encode(chunk) for chunk in split_77(prompt)], dim=1)   # 形状 (1, 154, 768)
```

收益：长提示词/长负向词不再被砍；负向词越完整，"多主体/印章/纸纹"压得越干净——正好对应 README 里反复出现的三个脏点。
成本：交叉注意力 seq_len 翻倍，512² 下约 +3~5% 耗时。

**顺带修**：`rough_tokens()` 用"1.35 token/词"估算，对 `photorealistic`、`anti-aliasing`
这类会被 BPE 切碎的词严重低估；`tokenizer(text).input_ids` 是免费的，直接数真值。

### Q3 步数策略：30 步是过采样，预算应该转成"候选数"

TDM 评测表（SD-v1.5，同一基座）：

| 方案 | 步数 | HPS↑ | Aes↑ | FID（风格保真）↓ |
|---|---|---|---|---|
| v1.5 原版 | 25 | 30.03 | 29.02 | — |
| LCM | 4 | 27.72 | 26.91 | 26.89 |
| **Hyper-SD** | 4 | **30.36** | 28.86 | **37.83** |
| TDM | 4 | 31.22 | 29.78 | 20.23 |

读法要小心：**Hyper-SD/TDM 在 4 步就能追平 25 步画质，但 Hyper-SD 的 FID 明显偏高**
（= 与教师模型的风格分布偏离大），而本项目是**重度 LoRA 依赖**（像素 LoRA 就是风格本体）。
上表 LoRA 集成那一栏里 Hyper-SD 的 FID 从 37.83 升到 38.70，说明风格漂移在 LoRA 场景下更明显。

**建议**：把"30 步 × candidates=2"改成"8~12 步 × candidates=4~6"，总耗时持平甚至更短，
但**挑帧空间翻倍**——而挑选恰恰是这个项目最擅长、且对最终质量最有效的环节（WSS 的补提逻辑就是证据）。
落地顺序：先 LCM-LoRA（成熟、风险低）→ 达标再试 Hyper-SD/TDM，**验收指标必须包含"像素单色率"和"身份相似度"**，
不能只看 HPS。

### Q4 主链路的后处理不是网格对齐的

`postprocess.pixelate()` = BOX 降采样 + NEAREST 放大，**不做网格检测**。
而 `pixelfy`/`perfect_pixel` 那套（FFT + Sobel 吸附 + 每格中位色）是同项目里质量更好的实现，
实测每格单色率 100%。结果就是：W1/W4 走的是"较差的像素化"，只有专门的 wpx 节点走"较好的"。

同一个仓库里两套像素化，较差的那套在主路径上。**建议把 `_postprocess` 的 pixel 分支换成
`pxf.refine_batch(target_size=...)`**，保留 BOX 路径作为 `grid_snap=False` 的退路。
风险：现有测试里钉了"像素块单色性"，换实现后需要同步更新预期——但这正是应该被换掉的。

### Q5 质量闸门评错了对象

`generate.py:1327-1349`：`_one_frame()` 先 `_postprocess()`（抠图→像素化→量化），
再把这个**已经量化到 32 色、128 有效像素**的图交给 `quality.evaluate()` 数关节。

姿态模型在像素化产物上检出率天然偏低 → 好帧被判不合格 → 触发无意义的补提
（`gate_retries=2`，每帧多烧 2 次生成）。README 里"8 帧里有 2 帧只提取到 8/18 关节"的记录，
很可能有一部分是**评估端**造成的，而非生成端。

**建议**：`coverage/edge` 用抠图后的图（需要 alpha），`points` 用**像素化之前**的抠图图。
两图中介物都不贵，帧级多存一张 768² RGB 而已（8 帧 ≈ 14MB）。

### Q6 SD1.5 + ControlNet 在 768² 上用，与权重训练分辨率不一致

OpenPose/Canny v1.1 是 **512²** 训练的。W4/WPC/WSS 默认 768² 直接推理，等于跨分辨率使用控制网：
控制力下降、肢体更容易糊（项目自己也记录过"768² 偶有肢体糊成一团"）。

业界的标准解法是**两段式**：512² 出结构（ControlNet 在训练分辨率上最准）→ img2img 1.5× 高清修复
（低 strength，或用 tile ControlNet）。项目里 tile CN 和 img2img 都有，只是没串成一条 w1/w4 的后半段。
收益：结构准确度 + 边缘细节都提升；显存峰值反而比 768² 单段更低（512 段是 2.6GB 级）。

### Q7 WSS 默认路径把 preset 拼了两遍

`generate.py:767` 先 `presets.build(...)`，再把 `preset=preset` 传给 `_sprite_animatediff`，
后者 `1068` 行又 build 一次。已复现：

```
单次: a green slime monster, full body, standing, centered, plain white background, single character
二次: ... single character, full body, standing, centered, plain white background, single character
```

77 token 的预算被白吃 15 个，用户描述一长，第二次 build 还会把用户正文按"已含契约"的尺寸再截一遍。
修法：只在最外层 build 一次（把 `_sprite_animatediff` 的 `preset` 参数置 None 传入，或干脆删掉该参数）。

### Q8 WPC / WSS 硬编码 `model="sd15"`

```
generate.py:668  eng.pose_pipe(..., model="sd15")
generate.py:810  eng.pose_pipe(..., model="sd15")
generate.py:1084 eng.animatediff_pipe(..., model="sd15")
generate.py:674/816  _skip_embeds(..., "sd15")
```

用户在设置里切到 SDXL，WPC/WSS 仍然跑 SD1.5，**无任何提示**。这是"切了底模没效果"的典型来源。
WSS 的签名里干脆没有 `model` 参数。建议：加参数并透传；SDXL 下若走 AnimateDiff（只支持 SD1.5）应显式报错而不是静默降级。

### Q9 抠图：模型代际 + alpha 策略一刀切

- `isnet-general-use`（2022）。细长结构（剑、法杖、飘带）与半透明部分的边界明显弱于 **BiRefNet**（rembg 已内置 `birefnet-general`）。
  README 说"alpha 都是二值所以 u2net 边缘软不是问题"——那是**像素化之后**的观测；对高清立绘/宣传图这条不成立。
- `quantize_palette` 与 `_postprocess` 一律把 alpha 二值化。这对像素素材正确，对**高清插画资产**是错的（会啃掉发丝/纱）。
  建议按 `pixel>1` 与否分流：像素路线保持二值，插画路线保留 8bit alpha 并做 1px 内缩去白边。

### Q10 w5 缺"差分扩散"这一层

w5 = 裁剪 → img2img(strength 0.9) → 羽化贴回。业界（Fooocus Inpaint / Differential Diffusion）的做法是
**把原图内容按蒙版软混合进每一步去噪**，好处是 strength 可以开到 1.0 仍保持选区外不变、且**没有接缝**——
不需要"羽化 4px + 边界色彩校正 + 色板吸附"这三层补丁。

项目里"选区外逐点不变"已经用测试钉死了，说明工程能力强；把混合从"末端贴回"移到"每步去噪"，
是同一目标下更优的实现。可作为 w5 的第二个引擎（`mode="differential"`）并行存在，用现有 A/B 工具对比接缝指标。

### Q11 IP-Adapter 只吃一张参考图

角色一致性目前靠单图 CLIP Vision 编码。业界成熟做法是**多图参考取平均 embeds**（同角色 3~5 张不同姿势），
实现上就是 `encode_image` 后对 batch 维求均值——改动 ~10 行，对"换角色保持身份"的稳定性提升明显，
且不增加显存（参考图编码本来就用完即退）。这与项目已有的 `refprep.prepare_reference` 天然契合。

## 3. 显存 / 内存

### M1 权重复制：同一个 UNet 在显存里存了两份（-2~3.3GB）

README 已经诚实记录了："7.36GB 是 txt2img 与 ControlNet 两套 pipeline 同时常驻的结果"。
根因在 `engine.py`：

- `img2img_pipe` 用 `cls(**self._cache[tkey].components)` 共享了组件（✅ 做对了）
- `pose_pipe` 走 `from_pretrained` **重新从磁盘加载了一份 UNet/VAE/TextEncoder**（❌）
- `inpaint_pipe` 是 9 通道 UNet，确实不能共享；但 txt2img / img2img / pose 三者完全可以共用一个 UNet

改法：`StableDiffusionControlNetPipeline(**txt2img.components, controlnet=cn)`，成本约 10 行。
预估：7.36GB → ~4.2GB（省 3.1GB），且 LoRA 只需加载一次（顺带缓解 M2 的 Q8/LoRA 问题）。

更彻底的做法是学 ComfyUI/A1111 的**单模型 + 运行时 patch**：一个 UNet 常驻，ControlNet/IP-Adapter/LoRA
都是"挂上去、用完摘掉"。这是当前业界让 24GB 卡跑 SDXL+3 个 ControlNet 的标准架构，但要重构 Engine，
建议放在 M1 之后按需推进。

### M2 `ensure_headroom` 的判据写反了 —— 缓存实质失效（已复现）

```python
def _used_gb(): return torch.cuda.memory_reserved() / 2**30
if _used_gb() < need_gb: return          # 已用 < 2GB 才返回
for key in ...:
    if _used_gb() < need_gb: break       # 一路丢到「已用 < 2GB」
```

这里的 `need_gb=2.0` 被当成了"已用量的上限"，而语义应该是"**还需要多少空闲**"。
只要加载了任何管线（≥2.6GB），条件恒成立 → **每次调用都把缓存清空**。复现输出：

```
ensure_headroom(need=2.0) 后剩余缓存: []
```

同时 `_ctrl`（ControlNet，1.4~2.4GB）**不参与驱逐**，于是"清空了缓存但显存没降到位"，
下次又得重新加载 UNet——`_ctrl` 成了隐形泄漏。

修法：
```python
free = (total - reserved) / 2**30
if free >= need_gb: return
for key in LRU 顺序（排除 keep 与即将使用的那条）:
    驱逐 + 清 _ctrl 对应项 + empty_cache
```
注意 README 里"加了驱逐后峰值回到正常水位"的观测**与这个 bug 是自洽的**——水位确实降下来了，
代价是每次 wss/wpc 都重载权重，这部分成本没被计时，所以没被发现。

### M3 24GB 卡只用了 2.6GB —— 该"花钱买速度"而不是省显存

| 用例 | 峰值 | 24GB 利用率 |
|---|---|---|
| W1 512² | 2.61GB | 11% |
| W1 768² | 3.36GB | 14% |
| W4 + IP-Adapter | 10.59GB | 44% |

**全程 batch=1**（`grep num_images_per_prompt` 无命中）。而 candidates=2/3 是串行跑的两次独立前向。
把候选合成一次 batch 调用（`num_images_per_prompt=N` + 每样本独立 generator），输出与逐次生成**逐像素一致**
（SD 无跨样本注意力），预估 512² 下 1.5~1.8×、768² 下 1.25~1.4× 吞吐。
W4 的 8 帧同理可批 4 帧一组（同一 ControlNet、不同条件图），8.07s 有机会压到 5s 内。

这一步的意义：**把省下来的显存换成候选数**，直接提升成品率——比继续抠显存更划算。

### M4 VAE 解码优化只做了 AnimateDiff 一条线

`vramopt.apply_vae_slicing` 只在 `animatediff_pipe` 里调用。SDXL 1024² 的 VAE 解码峰值约 1.5~2GB，
W3+SDXL、W1+SDXL 都没开。另外 SDXL + Tile CN 实测 **21.94GB**（距 24GB 只剩 2GB），
建议：

1. 所有管线统一 `pipe.vae.enable_slicing()`；1024² 以上再加 `enable_tiling()`
2. SDXL 场景加**重量化**选项：`torchao` int8 weight-only 或 fp8 权重，SDXL 权重 6.5GB → 3.5GB 左右，
   Tile CN 那 21.94GB 有机会降到 13~14GB（4090 是 Ada，int8/fp8 权重有硬件支持；需 A/B 验证画质）

### M5 没有 OOM 恢复梯度

`_fit()` 只在 `.to(device)` 时捕获 OOM，且只降级到 `model_cpu_offload`（项目自己实测过这条路**峰值反而更高**）。
生成本身 OOM 时任务直接 failed。业界做法是**捕获 → 驱逐 → 降参重试**：

```
try: 生成
except OutOfMemoryError:
    eng.free(keep=(当前管线,)); 分辨率 -64 / 步数 ×0.8; 重试（最多 2 次）
```
对于 20 角色的关卡批量任务，这一条能把"跑到一半挂掉"变成"自动降档跑完"。
`vramopt.plan_generation` 已经有降分辨率的逻辑，复用它即可。

### M6 训练线程与生成 worker 抢同一张卡

`app.py:134` 起生成 worker，`app.py:195` 训练又起一个独立线程——注释说"绝不能塞进生成队列把出图全卡住"，
但**它仍然在抢 GPU**：训练 4.67GB + 生成 5.78GB + 上下文，很容易撞顶。
建议：训练与生成共用一个 `torch.cuda` 级互斥锁（或训练期间把生成 worker 暂停），
把"不阻塞队列"降级为"不并发占卡"。这是架构正确性问题，不是调优。

### M7 索引与任务表会无限增长（内存 + 延迟）

`app.py:260-283` 每次 `/assets` 都**全量读 `index.jsonl` + 逐行 json.loads + 逐个 `Path.exists()`**。
当前 2.6MB / 2974 条（≈880B/条，因为 wss/w4 的 `frame_scores` 全量入库），
按每角色 32 帧的产线节奏，3 万条约 26MB —— 每次打开画布都解析一遍，且阻塞主线程。

同时 `_jobs` / `_trains` 两个 dict 无上限、无 TTL，长跑服务会持续吃掉 RAM（每条 job 含完整 result/meta）。

建议：索引换 SQLite（`file, scope, workflow, created, meta_json` + 索引列），启动建表、写入同步；
`_jobs` 改 `OrderedDict` 保留最近 200 条。改动小、收益确定。

### M8 小项

- `vramopt._RELEASED_ENCODERS` 用 `id(enc)` 做键，对象回收后 id 可能被复用 → 误判"已处理"而跳过 `to("cpu")`。改 `WeakSet`/`id` + 引用一起存。
- `_fit()` 的 docstring 写"降级顺序 attention_slicing → vae_slicing → model_cpu_offload"，代码只做了最后一步。文档与实现不一致，建议要么实现要么改注释。
- 每次任务结束缺一次 `torch.cuda.empty_cache()`（长跑时 reserved 会阶梯式上涨）。
- `models/checkpoints/sd15` 是 fp32 目录（4.2GB），`detect_variant` 返回 None → 加载时 RAM 峰值 ~4GB 并现场转 fp16。可以直接存 fp16 变体，加载快一倍。
- `poseswap` 没调 `ensure_headroom`，而 wss/wpc 调了 —— 行为不一致（虽然当前实现是"过度驱逐"，反而没暴露问题）。

## 4. 架构级建议（可选，收益最大但改动大）

**A. 用已有的 Wan2.2 出动画序列，而不是 AnimateDiff。**
项目 W5 实测：25 帧 @384² = 26.8s（**1.07s/帧**）；而 WSS 的 AnimateDiff 是 8 帧 7.4s（0.925s/帧）。
**吞吐几乎相同**，但视频底座的时序一致性与画面质量明显优于 SD1.5+AnimateDiff，
且不存在"motion module 在 num_frames=1 时畸形、要跑 2 帧取第 1 帧"这类补丁。
代价：控制粒度下降（若要严格跟随参考动作需要 VACE/Fun-Control 这类可控视频模型）。
建议作为 WSS 的第三个引擎 `engine_mode="video"`，用现有 `silhouette_drift` 指标直接对比。

**B. 生成与后处理解耦成可组合的 stage。**
现在 9 个 workflow 各自把"生成 + 后处理 + 落盘"写在一起（`generate.py` 1399 行），
导致 Q4 那类问题要改 5 处。抽成 `generate_stage → postprocess_stage → export_stage` 后，
"主链路用网格对齐"这种事只改一个地方。这是可维护性投资，不直接提质。

**C. 把"候选 + 闸门"做成通用层。**
W4 用关节数、WSS 用剪影 IoU，两套评分不通用，W4 对非人形角色恒为 0。
统一成"可插拔 scorer 列表"（pose / silhouette / identity / clip-sim），W4 在检出不到人体时自动切剪影评分。

## 7. 值得保留的设计（评审中确认正确）

1. **羽化只向内**（`postprocess.composite` / `repaint.composite`）：`soft * inside` 保证选区外权重恒为 0，
   这是可逐像素验证的承诺，比业界多数"软蒙版随手糊一下"的实现严格。
2. **每格中位色采样**：`perfect_pixel` 的中位色 + 网格吸附，实测 100% 单色率，优于 BOX 降采样。
3. **锚点只平移不缩放**：`align_sequence` 保住了下蹲/抬腿的真实大小变化，这个判断很对。
4. **"没有判据 ≠ 不合格"**：闸门在模型缺失时关闭而不是无限重提，避免烧卡。
5. **A/B 工具化**：`tools/ab_*.py` 五件套 + 单变量原则，是这个项目最值钱的工程资产，Q1/Q3/Q10 都应该挂在这套工具上做。

### 两条被自己推翻的结论（保留原文以示审计）

1. **Q4 的前提不成立。** 主链路的输入是连续调 AI 图，**根本没有可检测的网格**：

## 9. Q1 的落地：基座 A/B 工具与首轮实测

Q1 的结论是「画质主因是基座权重」，但"哪个基座更好"不能靠肉眼下结论——那正是确认偏差
最容易生效的地方。所以这一节交付的不是一个新基座，而是一套**可复现的判据**。

### 工具

`tools/ab_base.py`：多基座 × 6 条产线 prompt × N seed，全部走**产线同一套后处理**
（`generate._postprocess`），所以量到的就是真实废片率。

```bash
python tools/ab_base.py --size 768 --steps 20 --seeds 3     # 口径一致，可直接比权重
python tools/ab_base.py --rebuild --out assets/_ab_base     # 只重建报告，不重跑
```

指标：`subjects`（前景连通域数）、`edge`（贴边）、`fg`（前景占比）、`uniform`（块单色率）、
`colors`、`white`（背景白净度）、`points`（姿态关节数，仅类人形）。

### 首轮结果（RTX 4090）

**A 组：各基座用各自甜点尺寸**（sd15 512/20、SDXL 1024/24，24 张）

| 基座 | 多主体率 | 贴边率 | 背景脏率 | 块单色率 | 人均关节 | 均耗时 |
|---|---|---|---|---|---|---|
| sd15 | 0% | 83% | 83% | 1.000 | 10.3 | 0.75s |
| sdxl | 17% | 8% | 75% | 1.000 | 17.7 | 3.52s |

**B 组：统一 768² / 20 步**（排除尺寸混杂，24 张）

| 基座 | 多主体率 | 贴边率 | 背景脏率 | 块单色率 | 人均关节 | 均耗时 |
|---|---|---|---|---|---|---|
| sd15 | 17% | **50%** | 100% | 1.000 | 14.0 | 1.33s |
| sdxl | 8% | **0%** | 92% | 1.000 | 18.0 | 1.77s |

逐 prompt 多主体率（B 组）：sd15 在 `prop`、`portrait` 各 1/2 翻车；SDXL 只在 `mech` 1/2。

### 三条结论

1. **base v1.5 的问题是"废片"，不是"不好看"。** `knight` 这个 prompt 它画成了半身特写
   （头顶被切、无全身），斗篷糊成一坨，第二个 seed 直接姿态崩坏。这是**基座知识覆盖**
   的问题，不是提示词能救的——印证了 Q1 的判断。
2. **统一口径下 SDXL 的结构完整性明显更好**：贴边 0% vs 50%，人均关节 18.0 vs 14.0。
   但多主体率两者都不为 0，说明"换更好的基座"也消不掉这条，仍需候选 + 闸门兜底。
3. **"SDXL 慢 3~4 倍"这个论据站不住。** 同分辨率下只慢 **1.33 倍**（1.77s vs 1.33s）；
   那个 3~4 倍是 512 vs 1024 的**尺寸差**。真正制约 SDXL 的是显存（+Tile CN 21.94GB），
   不是速度。这条修正了 README「版本选型」里的一处归因。
